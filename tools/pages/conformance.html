Conformance & evidence

Every number names its corpus, its command and its caveat

Broiler runs seven distinct evidence suites against different corpora, with different blind spots. This page collects what each one measures, what it cannot see, and the figures the repository actually records — including the unflattering ones.

The rule that governs this whole page

Passing unit, test262, WPT or visual-comparison tests is useful evidence, but it does not prove that a component is secure or defect-free. A published claim must name its corpus revision, environment, metric, tolerances, skips and reproducible command; a regression must be assigned to one owning component. A checked historical task is not release or conformance evidence.

Web Platform Tests — the golden-image suite

Every shard downloads Chromium through Playwright, screenshots each test, and compares Broiler's render against that PNG. The default pass threshold is a 99% pixel match — at most 1% differing pixels — configurable through --pass-threshold or BROILER_WPT_PASS_THRESHOLD. Per-test limits are a 30-second timeout and a 1024 MiB cap on the growth of the rendering process's resident set.

51Pixel gaps not fixed — each with an owner, evidence and an exit gate
50Closed gaps, recorded with root cause, what landed, and the wrong turns
17Tests Broiler renders correctly and the golden image does not

Four things that are true of the whole set

The gaps index opens with four warnings, and they are more instructive than the counts.

  1. A 0.0% is as likely to be a reference disagreement as an engine gap. The suite scores Broiler against a Chromium screenshot, so a feature Chromium lacks scores zero permanently — shipping a feature moves the test down. The run now detects this itself and reports those failures under Not ranked — reference disagreements instead of ranking them; one run flagged 40.
  2. A suspectReference flag is a triage queue, not a verdict. Of 28 flags nobody had checked by hand, 25 were wrong — 17 of them because Broiler rendered a blank canvas for the test and for its reference, and blank matches blank at 100%. The --verify-reference check never asked whether anything was drawn. It does now.
  3. Passing a test's own reference is necessary, not sufficient. One subgrid test passes its rel=match at 100% because the test and its reference share the broken layout. The inverse exists too: two view-transition tests pass on CI and are demonstrably wrong.
  4. A patch number identifies nothing. The retired patches/ directory was a backlog rather than an archive — a file was deleted once its fix was upstream and numbering restarted from 0001 — so the same number named different changes at different times. One gaps document accumulated 25 dangling references before it was called out. Fixes are identified by commit subject.

Timeouts are the failure the pixel suites cannot see

A timed-out run is abandoned before it renders, so it is invisible to every pixel comparison — and it costs the shard its whole budget in wall clock. A run of 65 timeouts was analysed, and almost none of them was what its directory name suggested.

Six of the seven causes were one shape

Something walks the document — elements, insertions, geometry reads, animation frames — and each step redoes work whose cost is the whole document: a stylesheet discovery walk, a style invalidation, a layout, a clone-and-cascade. Nothing is wrong with any single step; the product is what misses the budget.

So when a timeout has no obvious infinite loop, the question is not "what is stuck" but "what is being redone once per element?" — and the way to answer it is to render synthetic documents of N, 2N and 4N elements and difference the times, which cancels fixed startup cost. An exponent near 2 says the loop is the bug, not its contents.

Some tests need no reference image at all

A WPT test carrying data-expected-* / data-offset-* states its own expected geometry, so one render can judge it. The pixel suite can only skip these, which means a CI mismatch percentage says much less about them than their own assertions do.

judge a check-layout test from one render
dotnet run --project src/Broiler.Wpt -- --wpt-dir tests/wpt/checkout \
  --check-layout --render <FILE>
# prints  check-layout: N/M passed (±1px)  and lists each failure

Web Platform Tests — the reftest suite

A second, independent suite that uses no other rendering engine. A WPT reftest states its correct rendering inside the checkout, as a link in the test document:

a reftest declares its own answer
<link rel="match"    href="foo-ref.html">    <!-- must render identically to this -->
<link rel="mismatch" href="bar-notref.html"> <!-- must NOT render identically to this -->

The reference is deliberately written to produce the same picture using only features the test does not exercise, so one engine can check the pair on its own: render the test, render the reference, compare the bitmaps. Broiler is on both sides.

Golden imagesReftests
BaselineChromium screenshot of the testBroiler's render of the test's declared reference
Tests runEvery discovered documentOnly those declaring a reference
Needs a browserYes — Playwright Chromium, cachedNo
A failure can beA real bug, or a font/scrollbar/antialiasing difference between engines, or a stale goldenA real disagreement with what WPT says the test should look like
Blind spotChromium missing the feature under testA bug that hits the test and its reference alike

Their pass rates are not comparable. The trade is worth stating plainly: this suite cannot catch a defect that damages the test and its reference identically. In exchange nothing is ever attributed to Broiler that is really a cross-engine rendering difference, and a run needs no browser download — which also removes a browser-provisioning outage the golden-image suite has to defend against.

A test that fails the golden-image suite but passes here is evidence the golden, not the engine, is the outlier. The converse is a real defect the Chromium comparison happened to mask.

run the reftests
./scripts/run-wpt-reftests.sh --wpt-dir tests/wpt/checkout
# or
dotnet run --project src/Broiler.Wpt -- --wpt-dir <dir> --reftests-only

test262 — the ECMAScript suite

Broiler.JS is validated against the official TC39 suite, and conformance is tracked continuously in CI. What is checked in is the evidence surface — the runner's capabilities and its self-checks — rather than a headline number.

No release totals are recorded

The dashboard's release-evidence and comparative-engine tables both read "No current release-candidate run recorded." A total belongs there only when it links to raw artifacts from an exact Broiler commit and an exact upstream suite revision. A row may never claim "100% compliant" unless every supported host mode is green and every excluded category is explicitly outside the product claim. The checked-in failure manifest is a queue, not an allowlist of acceptable release behaviour.

Three properties of the runner are worth singling out:

  • A caught error is not an answer. Async completion uses a marker protocol — explicit success, explicit failure, or the runner's timeout. A test that never settles, settles twice, or reports a failure is a failure.
  • The protocol checks itself. Fixtures that must fail are run before every CI shard, and any mismatch fails the job.
  • Exclusions are per-hook, not per-area. $262 defines global, createRealm, detachArrayBuffer, evalScript and gc; a test is excluded only for a hook it needs and does not have.

Real-world website renders

Nine public pages people actually use — Google Search, 7-Zip, heise online, Wikipedia, MediaWiki, GitHub, MDN, Hacker News and W3C — captured at a fixed 1024×768 viewport, with screenshots, diffs, logs, machine-readable results and a detailed report published.

It is deliberately observational. A live website can change its HTML, experiment assignment, consent page, advertisements, news, fonts or anti-bot response without a Broiler commit, so the weekly workflow reports missed thresholds but does not fail on them by default.

Three renders per case, two comparison lanes

RenderWhat it isDecides pass/fail?
Chromium referencePlaywright visits the live URL in a fresh context with fixed viewport, locale, timezone, colour scheme, reduced motion and device scale, recording final URL, status, versions, errors, timings, serialized DOM and screenshotIt is the baseline
Broiler liveBroiler.Cli --capture-image against the same public URL — end to end, including networking, HTML, CSS, JavaScript, layout and paintingYes
Broiler replayBroiler renders the final DOM Chromium recorded, after scripts, inline handlers, refresh/CSP metadata and embedded-document navigation are neutralized and a <base> is insertedNo — it is isolation evidence

A poor live result with a good replay points toward input loading or script execution; a poor result in both lanes points toward layout or painting. The replay is not a bit-for-bit web archive — external styles, images and fonts can still change or fail, and serialized DOM does not preserve canvas pixels, closed shadow roots or every JavaScript object.

Three primary metrics, and why

  • Pixel match — percentage of viewport pixels whose RGBA channels differ by at most the tolerance (5 by default, matching the WPT runner).
  • Content match — the same tolerant match restricted to the union of the two images' non-background pixels. This prevents a mostly white viewport from calling a visibly broken page "97% pixel-perfect."
  • Structure match — edge precision/recall F1 with one pixel of spatial tolerance. Sensitive to missing text, controls and layout, and less dominated by flat backgrounds.

A live result meets quality only when its dimensions match and all three primary metrics meet their thresholds. Stable and dynamic sites are summarized separately, and dynamic pages are never presented as a standards-conformance rate.

Case study — the Vector 2022 skin

38.9% → 82.7% of pixels, and what the honest summary is

mediawiki.org loaded and painted but did not look like the same page. The Vector 2022 skin turned out to be a useful witness because it stacks ordinary constructs — a flex header, calc() breakpoints, a floated display: table thumbnail, a JavaScript bootstrap that rewrites the page — and the reference browser handles all of them without comment, so every disagreement was Broiler's. Twenty-odd general engine defects came out of it: a calc() breakpoint that made 25 @media blocks malformed, floated flex items taken out of flow, a margin collapse spent twice, bold and italic resolving to the regular face.

The per-fix deltas are not additive, and are not quoted as such. Several defects compensated for each other — a header 16px too short sat above a site notice 17px too tall, so fixing either alone moved the page further from the reference. Three of the margin-collapse fixes each scored worse than the state before them, and only the third made the page align. The honest summary is the endpoints.

The measurement was taken against an offline mirror rather than the live page, because a live-vs-live comparison mixes engine differences with content differences. Broiler's own render of the live page and of the mirror agree, so the mirror is not flattering the result — it removes a source of noise.

The DuckDuckGo privacy test pages

A public corpus that asks a browser to exercise the parts of the platform privacy features act on: client-side storage, the request paths a page can open, the fingerprinting surface, HTTPS upgrades, and referrer and tracker handling. Each page runs its own probes and publishes the outcome in a results global — so what a run reports is what the page computed, not a rendering of it.

Every page is run twice: once by Chromium through Playwright and once by Broiler, from the same manifest and the same expressions. The two payloads are compared probe by probe.

63 of the 69 gaps are on the fingerprinting page, because it is the page whose probes are synchronous reads of the platform surface.

Two things the comparison had to learn first

Both were found by disbelieving a flattering number, and both are fixed in the runner.

A caught error is not an answer

These pages run each probe in a try and store the error object where the result belongs — so {"name": "ReferenceError", …} is, to a naive reader, a perfectly good value. The first comparison reported 92 probes in parity on the fingerprinting page; 40 of them were Broiler throwing.

A page that has not started yet holds very still

Several pages seed one entry per probe the moment they start and fill values in as third-party requests complete. A capture that stops when the results array stops changing can therefore stop before the page has begun.

This measures coverage, not privacy

A probe that produces a value is one Broiler was able to carry out; a probe that produces nothing is a platform gap. Nothing here is a privacy result for Broiler — including agreement with Chromium, which means Broiler carried the probe out, not that it made the right privacy choice. "Broiler reported a navigator.userAgent" is coverage; whether that string is a good answer for a shipping browser is a product question this suite does not answer.

The Acid tests

Acid2 was measured at 99.42% overall pixel match and 80.00% content-area match (18,346 of 22,932 pixels) at 1024×768, with zero red pixels — the CSS failure indicator — in both Broiler and Chromium. The face renders including the nose (98.82%), chin (100%) and smile (74.56%).

That roadmap is deprecated, and the figure is dated

The Acid2 compliance roadmap was superseded and is retained for historical context only; its last verification was 2026-04-04. The root roadmap is explicit that a 100/100 Acid script score does not establish current pixel fidelity or broad standards conformance, and that fresh Acid1/Acid2/Acid3 viewport references still need capturing, with script score, geometry, content and pixel metrics reported separately.

The investigation behind that number is a good example of how the project reasons. The original hypothesis — that the layout bitmap height was too small — was investigated and disproved. The real cause was a post-processor stripping all <table> elements: intended for Acid3's document.write() tables, it also destroyed the Acid2 table that implicitly closes a <p>, after which the fixed-position paragraph swallowed the entire face.

Unit-test status

Nothing in the aggregate repository's CI runs dotnet test

Its workflows are preview packaging, NuGet packaging, Octane, real-world renders, WPT reftests and WPT tests. The WPT workflows run the standards runner and score it against a baseline — a different thing from the hand-written xUnit coverage of that runner, which is gated nowhere. So a change can turn an xUnit test red and land. That mechanism is the cause of most of what is listed below, and it is worth fixing before the list is.

Measured on Linux, 4 cores, 16 GB, .NET SDK 10.0.302, submodules at the pinned pointers. The Broiler.Documents.* and Broiler.UI.* suites moved out with their components and are now run by those submodules' own solutions; the application suites live with the applications. Some Wpt_*_MatchesReference tests can fail in a bare container because of font differences — baseline before attributing a failure to your change.

Reproducing a run

WPT golden images
dotnet run --project src/Broiler.Wpt -- \
  --wpt-dir tests/wpt --reference-dir tests/wpt/references \
  [--subset <path>] [--failure-images <dir>]
real-world renders
(cd tests/wpt && npm ci && npx playwright install --with-deps chromium)
python -m pip install --requirement tests/real-world-sites/requirements.txt
export NODE_PATH="$PWD/tests/wpt/node_modules"
python scripts/run-real-world-render-tests.py --sites mediawiki
privacy test pages
python scripts/run-privacy-test-pages.py                  # every page, both engines
python scripts/run-privacy-test-pages.py --pages fingerprinting,gpc
python scripts/run-privacy-test-pages.py --no-reference   # Broiler only

Regenerate a privacy baseline deliberately with --update-baseline, never to clear a red run. The corpus is live, so additions, upstream removals and gaps never fail a run — only a probe that stops producing a value is a regression.

What is still owed

  • A reproducible Chromium baseline. Chromium 148 is captured in a lock file, but its WPT revision is unresolved and there is no published root snapshot or alignment workflow. The WPT and Octane workflows are still pinned to floating master rather than reviewed commit SHAs.
  • Fresh Acid, Google and WPT evidence. The April 2026 HTML and CSS WPT result snapshots were retired — they were a point-in-time report, not reproducible current evidence — so there is now no checked-in substitute for a fresh run.
  • A local HTTP fixture for the remaining Acid3 status and content-type cases.
  • Cross-checking the golden-image suite against the engine-independent one, systematically rather than case by case.
