Packages

Take one component, not the platform

The reusable component libraries publish as NuGet packages, versioned in lockstep at 0.1.0-preview.1 and licensed under Apache-2.0. There is no bundle of the whole platform — an application takes the abstractions it needs plus exactly the implementations it composes.

Prerelease, and gated on human review

0.1.0-preview.1 is a prerelease, so every install needs --prerelease. Public APIs and behaviour are not frozen and may change before 1.0. Public release is gated on the per-component HUMAN_REVIEW.md records — see Assurance before depending on any of this in anything that matters.

Quick install

the common cases
dotnet add package Broiler.Layout --prerelease                  # the layout engine alone
dotnet add package Broiler.UI.All --prerelease                  # the whole UI toolkit
dotnet add package Broiler.Media.All --prerelease               # the cross-platform media stack
dotnet add package Broiler.Input.All --prerelease               # the neutral input contracts
dotnet add package Broiler.Graphics --prerelease                # the neutral rendering core
dotnet add package Broiler.Graphics.Windows --prerelease        # + the Direct2D backend
dotnet add package Broiler.Documents.Rtf --prerelease           # one document codec

What is deliberately not published

Not publishedWhy
The three applications
Browser, Writer, Code		 They are products, not libraries. Their release workflows upload build artifacts for manual testing and create no GitHub release; store-ready signed preview packages come from the aggregate repository's packaging workflow, which owns the signing material.

Feeds and the package-source mapping

Each component repository's NuGet.config pins two sources — nuget.org and the Broiler-Platform GitHub Packages feed — and clears whatever the machine has configured, so a restore resolves identically everywhere. Package source mapping sends Broiler.* to either feed and everything else to nuget.org only.

That mapping is load-bearing

GitHub Packages requires authentication even for public packages and answers 401 to an anonymous request. An unmapped source would therefore be queried for every package and break the restore. Because the repositories take their Broiler dependencies through submodules as project references, nothing queries that feed today and no credentials are needed to build.

To actually pull Broiler.* from GitHub Packages you need a personal access token with the read:packages scope. Put it in your user-level config, never in the committed one:

user-level credentials
dotnet nuget update source broiler-github \
  --username <github-user> --password <pat> \
  --store-password-in-clear-text \
  --configfile "$APPDATA/NuGet/NuGet.Config"

In GitHub Actions use secrets.GITHUB_TOKEN rather than a personal token.

What every package ships with

  • XML documentation and a .snupkg symbol package.
  • A deterministic build with SourceLink.
  • A vendored eng/Broiler.Packaging.props — a copy of the suite-wide packaging metadata that holds the version. Edit the canonical file and re-run the sync script; never edit a copy.
  • Apache-2.0, except where a file or third-party notice says otherwise.

How publishing works

Each component's publish.yml is manual by default and chooses a feed — GitHub Packages or nuget.org. It defaults to a dry run that packs and attaches the packages without pushing. Pushing a v* tag publishes to nuget.org, and the tag must match the version in eng/Broiler.Packaging.props, which stays the source of truth for the suite version.

Packing is per configuration where a component builds platform-specific assemblies. Graphics needs three runs into one output directory; Input needs two, and because the builds are deterministic the second reproduces the first byte for byte.

packing the full graphics set
dotnet pack Broiler.Graphics.slnx -c Release         -o ./artifacts
dotnet pack Broiler.Graphics.slnx -c Release-Windows -o ./artifacts
dotnet pack Broiler.Graphics.slnx -c Release-Linux   -o ./artifacts
