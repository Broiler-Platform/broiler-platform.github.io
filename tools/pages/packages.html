For developers

Packages

Take one component, not the platform

All eighteen component libraries publish as NuGet packages on nuget.org, as 0.1.0-preview.N prereleases. The versions are not in lockstep: each repository numbers its own previews. There is no bundle of the whole platform — an application takes the abstractions it needs plus exactly the implementations it composes.

Prerelease, and mostly unreviewed

Every package is a prerelease, so every install needs --prerelease. Public APIs and behaviour are not frozen and may change before 1.0. Being on nuget.org says nothing about human review. The review records are revision-scoped and most read PENDING or cover an older commit; Broiler.VM's eight packages were published while its HUMAN_REVIEW.md read PENDING, and Input, Media, Documents and Native publish with no review record at all. Read Assurance before depending on any of this in anything that matters.

Quick install

the common cases
dotnet add package Broiler.Layout --prerelease                  # the layout engine alone
dotnet add package Broiler.HTML.Image --prerelease              # render HTML to bitmaps and PNG
dotnet add package Broiler.JavaScript.All --prerelease          # the whole JavaScript engine
dotnet add package Broiler.UI.All --prerelease                  # the whole UI toolkit
dotnet add package Broiler.Media.All --prerelease               # the media stack
dotnet add package Broiler.Input.All --prerelease               # the neutral input contracts
dotnet add package Broiler.Graphics --prerelease                # the neutral rendering core
dotnet add package Broiler.Graphics.Windows --prerelease        # + the Direct2D backend
dotnet add package Broiler.Documents.Rtf --prerelease           # one document codec

Versions: one sequence per repository

A repository's packages share one version, but each repository advances its own preview sequence — the publish workflow picks the next preview number nobody has used yet. So the numbers below have nothing to do with each other, and nothing waits for a suite-wide release. Checked against nuget.org on 2026-09-30:

Consumers pin their own versions, and the pins differ. On 2026-09-30 Broiler.HTML pins Broiler.Graphics at preview.7 while Broiler.Documents pins preview.6 and Broiler.Layout preview.5; Broiler.CSS and Broiler.Documents pin Broiler.Dom at preview.8, three behind the latest. A published PDF package is not a PDF feature

The PDF codec and its font and image providers are now packed and published as preview packages. In the component's words, package generation does not enable application features or certify PDF conformance: application integration keeps the read-preview and write-preview gates of the PDF support roadmap.

Broiler.VM — 8 packages

Published while the review record read PENDING

Eight packages were published to nuget.org on 2026-09-23, at 0.1.0-preview.4 and preview.5, while HUMAN_REVIEW.md read PENDING — and it still does: 0 of 5,773 relevant code units reviewed. The owner's rule recorded in the component's status ledger is that publishing a package may not proceed without a review decision. The ledger records the publication, moves no milestone for it, and leaves whether the prohibition is revised or the publication answered to the owner.

Feeds and the package-source mapping

Packages publish to nuget.org only; the Broiler-Platform GitHub Packages feed is retired. With the one exception listed below, every component repository's NuGet.config lists nuget.org alone, clears whatever the machine has configured, and maps every package (*) to it — so a restore resolves identically everywhere and needs no credentials. Cross-component dependencies are ordinary PackageReferences at versions each repository pins itself, not submodules or project references.

The retired feed still matters in one way: the preview numbers already spent there must never be reused. Some repositories record them as a VersionSuffix floor (Layout, CSS, HTML); others read the old feed as version history when they choose the next number (HtmlBridge, JSeal).

A stale cache can shadow nuget.org

NuGet caches packages by id and version only. A Broiler package once restored from a local or retired feed under the same version shadows the one on nuget.org, and the build then reports Broiler types as missing. Delete that version from ~/.nuget/packages/<id>/ and restore again.

The exceptions, on 2026-09-30:

  • Broiler Code's NuGet.config still maps Broiler.* to the GitHub Packages feed (broiler-github).
  • Broiler.Unicode's still lists both feeds and maps Broiler.* to GitHub Packages.
  • Broiler Plate's still lists the GitHub Packages feed, although its source mapping sends every package to nuget.org; its README still asks for a token that can read the feed.
  • Broiler.DOM's packaging guide still offers GitHub Packages as a publish target.

Where one of those needs the old feed, GitHub Packages requires authentication even for public packages: a personal access token with the read:packages scope, in your user-level config, never in the committed one:

user-level credentials
dotnet nuget update source broiler-github \
  --username <github-user> --password <pat> \
  --store-password-in-clear-text \
  --configfile "$APPDATA/NuGet/NuGet.Config"

Use the source name the repository's own NuGet.config gives the feed. In GitHub Actions use secrets.GITHUB_TOKEN rather than a personal token.

What every package ships with

  • XML documentation and a .snupkg symbol package.
  • A deterministic build with SourceLink.
  • A vendored eng/Broiler.Packaging.props — the shared packaging metadata: identity, licence, SourceLink and symbols. Its version is now only a default: publishing resolves an unused preview and passes it as an MSBuild override without editing the file. (The file's own header still describes a lockstep suite version; that no longer holds.)
  • Apache-2.0, except where a file or third-party notice says otherwise — Broiler.Net is Apache-2.0 AND MPL-2.0.

How publishing works

Each component's publish.yml targets nuget.org only. A manual run defaults to a dry run that packs and attaches the packages without pushing; pushing a v* tag publishes that exact version, which must be on the release line and unused. The workflow resolves the next unused 0.1.0-preview.N from nuget.org, reruns CI with it, proves that a clean consumer can restore the packages with nuget.org as its only feed, and only then pushes the .nupkg and .snupkg files.

Packing is no longer a run per platform configuration. Graphics' packaging guide calls the platform-suffixed solution configurations such as Release-Windows obsolete and builds Debug or Release only, as most components now do — but not all: the UI and Documents solutions still declare Debug/Release-Windows and -Linux beside plain Debug/Release, and HtmlBridge and JSeal add Debug-VM/Release-VM. Check the repository's own solution before assuming one. Every component packs with its own eng/pack.ps1, which checks package identities, versions, metadata, internal dependencies, documentation and symbols. Graphics' script enumerates every packable project, including platform providers excluded from the default build, and the complete set has to be packed on Windows because of the Direct2D backend:

building, testing and packing Graphics
dotnet build Broiler.Graphics.slnx -c Release
bash ./eng/run-tests.sh Release
pwsh -File eng/pack.ps1

HtmlBridge's and JSeal's -VM configurations switch their JavaScript engine to the Broiler.VM profile and change the project graph. The full procedure is in Graphics' packaging guide.
