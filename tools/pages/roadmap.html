For developers

Roadmap

What is unfinished, who owns it, and how it ends

The root roadmap tracks only work that crosses component or application boundaries. Everything else belongs to the component that owns it. Every item carries an owner, current evidence, a next action and an objective exit gate — a checked historical task is not release or conformance evidence.

The documentation rules that shape this list

  • Keep a roadmap item only while an outcome remains open. Remove completed implementation histories once any durable decision has been folded into an architecture or support document.
  • Give every item an owner, current evidence, a next action and an objective exit gate.
  • Put API and dependency rules beside the component that enforces them.
  • Record current support honestly. Local smoke evidence does not imply cross-browser, accessibility, hardware, security or production support.
  • New work enters the root file only when at least two components — or a root application/release workflow — must coordinate to close it.

Release and distribution

Publish a reproducible first preview

Evidence today: component package metadata, a packaging workflow, a lockstep preview version, SourceLink and symbol-package configuration, and commit-scoped review records.

Next actions:

  1. Validate installation from an isolated package feed without relying on the aggregate checkout.
  2. Ensure every release submodule pointer contains every required component commit. A release cannot depend on an out-of-tree patch.
  3. Complete exact-commit human, dependency, license, static-analysis and vulnerability review for the release graph.
  4. Configure the protected release environment and publishing credentials.
  5. Run the tag path and install the resulting packages and applications on clean supported hosts.

Exit gate

The exact reviewed commit produces deterministic packages and symbols, installs from the advertised feeds on supported platforms, passes the published smoke suite, and can be reproduced without uncommitted submodule changes.

What has shipped since, ahead of that gate

This item is quoted from the aggregate roadmap, which has not changed since 2026-09-10. The repositories have moved without it:

  • There is no lockstep preview version any more. Every component publishes to nuget.org at its own 0.1.0-preview.N — see Packages.
  • Broiler.VM published eight packages on 2026-09-23 while its HUMAN_REVIEW.md read PENDING.
  • Broiler Writer has public GitHub pre-releases — 0.1.0-preview.3, .4 and .5, 2026-09-22 to 2026-09-30 — although the Writer repository has no HUMAN_REVIEW.md. Its Windows and Linux builds are not code-signed; its Android packages are signed with the Broiler release key. preview.5 was published from a commit whose CI test jobs, on Linux and on Windows, failed.
  • Broiler Browser has a public GitHub pre-release, 0.1.0-preview.1 (2026-09-30), built from a commit whose CI passed. Its desktop builds are not code-signed; its Android packages are signed with the Broiler release key. Its HUMAN_REVIEW.md reads PENDING, as a summary only.
  • Broiler Plate has a public GitHub pre-release, 0.1.0-preview.2 (2026-09-22), not code-signed. Its review record, generated on 2026-09-30, reads PENDING, 0 of 248 units.

None of these publications went through the exit gate above: no exact-commit human review exists for any of them. They were published ahead of it.

Deliver installation and update paths

The repository builds portable Windows and Linux applications, but the proposed native installation and self-update system is not a completed product surface.

  • Freeze product identifiers, release channels, artifact names, signed manifest format, update ownership, rollback behaviour and key-rotation policy.
  • Ship deterministic signed portable releases before adding an in-app updater.
  • Add an atomic per-user portable install/update transaction with recovery and uninstall behaviour.
  • Add Windows and Linux native delivery only after the portable transaction and release-signing gates pass.
  • Keep macOS delivery gated on native application, graphics, input, signing and notarization support.

Exit gate

Each claimed platform has one documented update owner, verified signatures and hashes, rollback after interrupted activation, clean repair and uninstall paths, and end-to-end release tests.

Standards and test infrastructure

Publish a reproducible Chromium baseline

Chromium 148 is captured in a lock file, but its WPT revision is unresolved and there is no published root snapshot or alignment workflow.

  1. Resolve and record exact WPT and test262 revisions.
  2. Pin the WPT and Octane workflows to reviewed commit SHAs instead of floating master.
  3. Publish one generated snapshot linking the lock, focused JS/HTML/bridge results, visual references and performance results.
  4. Automate the refresh without making unrelated checkouts download the full WPT corpus.

Exit gate

A clean checkout can reproduce the same corpus and focused results from immutable revisions, and an upstream refresh is a reviewable diff.

Re-establish current Acid, Google and WPT evidence

Focused regression tests exist and historical campaigns landed many fixes, but checked implementation tasks and a 100/100 Acid script score do not establish current pixel fidelity or broad standards conformance. The April 2026 HTML and CSS WPT result snapshots have been retired — they were a point-in-time report, not reproducible current evidence — so there is now no checked-in substitute for a fresh run.

  • Capture fresh Acid1/Acid2/Acid3 viewport references and report script score, geometry, content and pixel metrics separately.
  • Add a local HTTP fixture for the remaining Acid3 status and content-type cases.
  • Rerun Google and the broader public-site corpus through the real-world suite, recording actual milestone measurements rather than inferring compliance from API presence.
  • Cross-check the golden-image suite against the engine-independent reftest suite. A test that fails the golden suite but passes there is evidence the golden, not the engine, is the outlier; the converse is a real defect the Chromium comparison masked.
  • Keep prioritized WPT failures in generated reports and component roadmaps — root tracking should cover only cross-component runner, timeout, reference and ownership problems.

Exit gate

Every published claim names its corpus revision, environment, metric, tolerances, skips and reproducible command; regressions are assigned to one owning component.

Retire obsolete test suites and historical artifacts

A focused audit found several kinds of test code that no longer protect a supported behaviour — guards for a removed backend, reflection over assemblies that no longer exist, tests that assert nothing, and production toggles whose only remaining consumers are the tests for them. The whole production footprint of one such batch was four lines across two files.

The cleanup is evidence-driven in both directions

A filename containing phase, migration, obsolete or cutover is not sufficient reason to delete a test; retained cases are judged by the current behaviour or compatibility boundary they protect. The converse also holds — two suites suspected of holding duplicate methods held none.

Already-red suites are recorded explicitly, or every later "matches the recorded baseline" gate would be unfalsifiable.

WebRTC browser capability

Active design · implementation not started

Current evidence: WebRTC, media devices, getUserMedia, peer connections, data channels, ICE/STUN/TURN/DTLS/SRTP/SCTP/RTP and browser WebSocket are absent. Windows has reusable camera and microphone providers and deterministic fakes, but no browser composition, permission broker, live HTML media route or physical audio output. The current bounded load window can dispose a settled JavaScript session before a late RTC callback.

The roadmap is explicit that this is an implementation plan, not a support claim:

Until the gate passes, the globals stay absent

Broiler must not expose shape-compatible objects backed by no transport, capture or media behaviour. This is also why html5test.com still reports one JavaScript exception: that is the page's own WebRTC probe deliberately provoking a throw to detect the absent feature, and it must not be suppressed.

The shortest credible route:

  1. Make a document's JavaScript realm and event loop survive beyond the current bounded page-load window.
  2. Select and pin a maintained native WebRTC engine behind a Broiler-owned stable C ABI after a time-boxed evidence spike. Do not implement the protocol suite from scratch.
  3. Land neutral RTC contracts and deterministic fakes, then a data-channel vertical slice before device access.
  4. Add a real pinned wptserve/HTTPS/testharness lane, a direct and TURN network lab, Chromium/Firefox interop, native fuzz and sanitizers, hardware, performance and soak, package, SBOM and rollback evidence.
  5. Keep Linux and Android absent until their independent platform gates pass.

Broiler.VM bytecode execution

Broiler.VM owns its own sequencing. The root item records only the cross-component outcome: a NativeAOT-compatible execution host for verified bytecode, which is a host for language profiles rather than a language. Its status ledger, last updated 2026-09-28, now has eight milestones — VM-0 to VM-7, the newest being a native artifact form with in-process native execution — and records every one as In progress and none as Accepted: no row may reach Accepted while HUMAN_REVIEW.md says PENDING, and no relevant code unit yet carries a human decision. VM-7 meets no exit-gate clause yet.

The ledger also records that eight packages were published to nuget.org on 2026-09-23 while review read PENDING, against the owner's rule that publishing a package may not proceed without a review decision; it moves no row for that, and leaves the answer to the owner.

Android applications

Emulator-verified preview

Seven sub-items, A0 through A6: freeze the platform baseline, the graphics presentation backend, real touch/pen/IME input, touch-first interaction in Broiler.UI, the Writer head, the Browser head, and Android build/CI/delivery. The shared Activity/SurfaceView host, both applications, hardware-accelerated Canvas presentation, the input bridge, system-bar insets, the scoped-storage Writer flow and the workspaces all build and run on an API 36 x86_64 emulator.

Physical-device validation remains outstanding.

Linux application preview

  • Complete the supported graphics presentation path, input ownership migration, resize and device-loss handling, and deterministic fallback behaviour.
  • Run Browser and Writer smoke suites on the declared distro/driver matrix, including software rendering and permission-denied input cases.
  • Record package dependencies, evdev permissions, diagnostics, accessibility limitations and hardware evidence.

Exit gate

Browser and Writer install and run on the declared Linux matrix, produce comparable artifacts, shut down without leaked native resources, and publish an evidence-based preview support statement.

PDF conversion decision

The standalone process path is retired. Native PDF support is an explicitly composed, in-process Broiler.Documents.Pdf codec, and any reusable graphics, media, document-model or pagination work belongs in its neutral owner.

The base slice is implemented — syntax, cross-references, object streams, the Flate/ASCIIHex/ASCII85/RunLength filters, logical text import and a deterministic PDF 1.7 writer — built only from what the repository implements itself, with no third-party runtime dependency and no bundled font or codec asset. Every remaining PDF technology is detected, skipped with its own stable diagnostic, and reachable by composing a reviewed implementation.

Exit gate

The obsolete CLI/process path stays absent; the codec stays unpacked and unregistered until the read-preview and write-preview gates pass; and PDF behaviour is advertised only after the implementation, corpus, security, interoperability and clearance gates pass. Enabling PDF in an application head means building the shared contracts first, not referencing the package.

That gate, too, is the aggregate roadmap's text, and the owning component has since moved past its first half. Broiler.Documents now packs the codec and its font and image providers and publishes them to nuget.org as preview packages; its PDF support roadmap says packaging is separate from application readiness. On the application side, the same roadmap records that the Windows and Linux Writer heads register the codec for opening, while its read-preview integration row still lists the exit-gate evidence as outstanding — and those Writer heads are in Writer's public pre-releases.

Maintenance policy

  • Completed implementation records are removed once durable decisions and open work have moved to their owners.
  • A required submodule change must be merged and present in the pinned component commit. Blocked work is recorded once in its owning roadmap or status record, with a reopening condition.
  • Generated test reports and comparison images belong under tests/ or the ignored artifacts/ directory — never under docs/. A committed baseline that no harness compares against is a prose journal in a binary format.
