For developers

Get started

Clone it, build one slice, run the tools

Broiler is a large graph, and it is deliberately split so you never load more of it than you are working on. Each application and component now builds from its own repository with a plain clone; the aggregate repository composes all of them when you want the whole thing.

Only want to try the apps? You don't need to build anything

Broiler Writer and Broiler Plate have public GitHub pre-releases — preview builds for evaluation and testing, whose desktop executables are not code-signed. The Browser's first release is still an unpublished draft, and Broiler Code has no release at all.

Get the source

To work on one application, clone just that repository. The Broiler components it is built on arrive as NuGet packages from nuget.org on the first build.

one application
git clone https://github.com/Broiler-Platform/Broiler.Browser.git
cd Broiler.Browser
dotnet build Broiler.Windows.Browser.slnx -c Release

Broiler.Writer builds the same way. Broiler.Code is the exception for now: only its Windows head builds from packages — see its developer page.

To have everything side by side, clone the aggregate repository. It composes 25 repositories as submodules — the components, the applications, and the newer Layout, HtmlBridge, JSeal, Net, Native, RegEx, DateTime, Unicode, VM, Plate, Mail and Fond repositories.

fresh clone of the aggregate
git clone --recurse-submodules https://github.com/Broiler-Platform/Broiler.git
cd Broiler
existing checkout
git submodule update --init --recursive

No repository nests checkouts any more

Between 2026-09-11 and 2026-09-18 every component except Broiler.DOM, which never had any, replaced its nested submodules with nuget.org package references, and Writer and Code did the same. At the commits the aggregate pins, none of the 25 records a submodule of its own. Graphics, UI, Writer, Code and Plate still carry a leftover .gitmodules file, but with no submodule commits behind it, so --recursive has nothing extra to fetch.

Five root solutions list projects that are no longer there

The 2026-09-29 restructuring deleted src/Broiler.HtmlBridge.* from the aggregate (HtmlBridge is its own repository now) and moved the JS and HTML pins past the removal of Broiler.JS's nested Broiler.{DateTime,Regex,Unicode} checkouts and of Broiler.HTML.Headless. The root solutions were not regenerated: Broiler.Cli.slnx, Broiler.Wpt.slnx and Broiler.Tooling.slnx each list 8 projects at paths that do not resolve, Broiler.Tests.slnx 9, and Broiler.Benchmarks.slnx 5. The aggregate has had no CI run on main since March 2026, so no build of them since the restructuring is on record — treat them as unverified. The application solutions and the platform-test solutions above resolve.

The applications live in their own repositories and are composed here as submodules, so their solutions are read out of those checkouts rather than from the aggregate root. Component-owned unit tests live in the component's own solution, inside its submodule.

The one extra Android setup step

net10.0-android projects need the .NET android workload plus the Android SDK. In the project's development container an idempotent script provisions both (about 4.5 GB), and it is deliberately not part of session start — most work never touches Android.

android sdk
scripts/install-android-sdk.sh
export ANDROID_HOME=/root/android-sdk ANDROID_SDK_ROOT=/root/android-sdk

Without the SDK, every net10.0-android project fails with XA5300: The Android SDK directory could not be found — including a resource-free class library, and setting AndroidSdkDirectory to a stub does not help. dotnet build -t:InstallAndroidDependencies is not a substitute here; the script drives Google's sdkmanager, a Java tool, which picks up the container's JVM truststore automatically.

android build with an explicit SDK path
dotnet build Broiler.Writer/Broiler.Android.Writer.slnx \
  -p:AndroidSdkDirectory="C:\Program Files (x86)\Android\android-sdk"

The tools

The aggregate's own tools reference removed paths

In the aggregate, src/Broiler.Cli and src/Broiler.Wpt still reference src/Broiler.HtmlBridge.* and Broiler.HTML.Headless, and src/Broiler.DevConsole references src/Broiler.HtmlBridge.Core — none of which exist any more. The WPT, real-world and privacy runners below build or look for those tools. The paths do not resolve, and no build since the restructuring is on record. The working command line is the one in Broiler.Browser.

Broiler.Cli — render, evaluate and analyse a page

The command-line renderer lives in the Browser repository now, at src/Broiler.Browser.Cli, and runs pages on the browser window's own pipeline. It captures a page and can evaluate expressions against the same JavaScript context. --diagnostic-dir is what to reach for when a page misbehaves: it writes every JavaScript failure to a streamed log — so a hang or timeout still leaves one — archives every page, script, stylesheet, fetch/XHR response and sub-document the run touched, and produces a summary.md ranking the distinct failures and the platform features the page asked for and did not get. --analyze goes further and writes a ranked report of what looks wrong with the page's HTML, CSS, JavaScript, layout, rendering and network.

capture with diagnostics, in a Broiler.Browser clone
dotnet run --project src/Broiler.Browser.Cli/Broiler.Browser.Cli.csproj -c Release -- \
  --capture-image https://example.com/ --output page.png \
  --diagnostic-dir ./diagnostics

dotnet run --project src/Broiler.Browser.Cli/Broiler.Browser.Cli.csproj -c Release -- \
  --analyze https://example.com/ --output-dir analysis

The full command reference is docs/command-line.md; more on diagnosing pages is on the Browser developer page.

Document round-trips and comparison

broilerdoc is src/Broiler.Documents.Cli in the Broiler.Documents repository (Broiler.Documents/src/Broiler.Documents.Cli in the aggregate). It composes the PDF codec read-only.

broilerdoc, in a Broiler.Documents clone

broilerdoc roundtrip report.docx --via docx --via odt --via rtf --via html --via markdown
broilerdoc compare a.docx b.docx --render --continuous --diff diff.png --tolerance 2

Things that will trip you up

A PackageReference version is a floor

Restore takes the lowest version nuget.org has at or above it, and resolves upward with NU1603 when that exact preview was never published. Component versions are no longer in lockstep either: each repository publishes its own next preview number. What a project actually got is in its obj/project.assets.json.

Three components have no dotnet test

Graphics, Media and Input use self-hosted console runners rather than a test framework, so there is nothing to discover. Build first, then run ./eng/run-tests.sh Release, which starts the runners.

Font differences can fail a render test

Some Wpt_*_MatchesReference tests fail in a bare container for that reason alone. Baseline before attributing a failure to your change.

Line endings in submodule sources

Several Broiler.HTML and Broiler.CSS files are CRLF, and some are mixed within one file. An editor that rewrites the whole file normalizes them, and a two-line change then reports two thousand. Check git show --stat after committing.
