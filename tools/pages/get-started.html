For developers

Get started

Clone it, build one slice, run the tools

Broiler is a large graph, and the workspaces are deliberately split so you never load more of it than you are working on. Pick the product, platform or validation slice you want and build that.

Get the source

Broiler uses recursive Git submodules.

fresh clone
git clone --recurse-submodules https://github.com/MaiRat/Broiler.git
cd Broiler
existing checkout
git submodule update --init --recursive

One component wants its submodules initialised by name

Broiler.UI asks you not to recurse: --recursive would walk the Media→Graphics cycle and fetch an unused Broiler.DOM as well. A project reference to a directory that is not there is only a warning during restore; the build then fails on missing types, which is a confusing way to discover an uninitialised submodule.

The solution map

The root workspaces are deliberately split so an IDE does not load unrelated applications, platform backends, tests, samples, generators and benchmarks. Each contains only its declared entry points and their transitive ProjectReference closure.

ScopeSolution
Browser applicationsBroiler.Browser/Broiler.{Windows,Linux,Android}.Browser.slnx
Writer applicationsBroiler.Writer/Broiler.{Windows,Linux,WebAssembly,Android}.Writer.slnx
Broiler CodeBroiler.Code/Broiler.{Windows,Linux}.Code.slnx
Hosted WriterBroiler.Office.Server.slnx
Rendering and WPT toolsBroiler.Cli.slnx, Broiler.Wpt.slnx
Developer toolingBroiler.Tooling.slnx
Integration testsBroiler.Tests.slnx
Platform testsBroiler.{Windows,Linux,WebAssembly,Android}.Tests.slnx
Performance harnessesBroiler.Benchmarks.slnx

The Browser, Writer and Code applications live in their own repositories and are composed here as submodules, so their solutions are read out of those checkouts rather than from the aggregate root. Component-owned unit tests live in the component's own solution, inside its submodule.

Build and test

the common slices
dotnet build Broiler.Browser/Broiler.Windows.Browser.slnx
dotnet build Broiler.Writer/Broiler.Linux.Writer.slnx
dotnet build Broiler.Code/Broiler.Windows.Code.slnx
dotnet test  Broiler.Tests.slnx
run the Win32 / Direct2D browser
dotnet run --project Broiler.Browser/src/Broiler.Browser.Windows/Broiler.Browser.Windows.csproj \
  --configuration Debug-Windows

Solution entry points are declared, not discovered

eng/solutions.json owns them. Regenerate and verify the dependency closures after changing project references — a hand-edited .slnx is silently reverted by the next generator run.

regenerate and verify solutions
./scripts/update-solutions.ps1
./scripts/verify-solution-projects.ps1

The one extra Android setup step

net10.0-android projects need the .NET android workload plus the Android SDK. In the project's development container an idempotent script provisions both (about 4.5 GB), and it is deliberately not part of session start — most work never touches Android.

android sdk
scripts/install-android-sdk.sh
export ANDROID_HOME=/root/android-sdk ANDROID_SDK_ROOT=/root/android-sdk

Without the SDK, every net10.0-android project fails with XA5300: The Android SDK directory could not be found — including a resource-free class library, and setting AndroidSdkDirectory to a stub does not help. dotnet build -t:InstallAndroidDependencies is not a substitute here; the script drives Google's sdkmanager, a Java tool, which picks up the container's JVM truststore automatically.

android build with an explicit SDK path
dotnet build Broiler.Writer/Broiler.Android.Writer.slnx \
  -p:AndroidSdkDirectory="C:\Program Files (x86)\Android\android-sdk"

The tools

Broiler.Cli — render and evaluate a page

The command-line renderer captures a page and can evaluate expressions against the same JavaScript context. --diagnostic-dir is what to reach for when a page misbehaves: it writes every JavaScript failure to a streamed log — so a hang or timeout still leaves one — archives every page, script, stylesheet, fetch/XHR response and sub-document the run touched, and produces a summary.md ranking the distinct failures and the platform features the page asked for and did not get.

capture with diagnostics
dotnet run --project src/Broiler.Cli -- \
  --capture-image https://example.com/ --output page.png \
  --diagnostic-dir ./diagnostics

Broiler.Wpt — the standards runners

golden-image suite
dotnet run --project src/Broiler.Wpt -- \
  --wpt-dir tests/wpt --reference-dir tests/wpt/references \
  [--subset <path>] [--failure-images <dir>]
reftest suite — no second engine needed
./scripts/run-wpt-reftests.sh --wpt-dir tests/wpt/checkout
dotnet run --project src/Broiler.Wpt -- --wpt-dir <dir> --reftests-only
judge one check-layout test from a single render
dotnet run --project src/Broiler.Wpt -- --wpt-dir tests/wpt/checkout \
  --check-layout --render <FILE>

Things that will trip you up

A plain dotnet build skips the platform backends

Platform projects build only under their own configuration. Pass -c Debug-Windows when you mean to check Direct2D, and -c Release-Linux for the OpenGL and Vulkan paths.

Three components have no dotnet test

Graphics, Media and Input use self-hosted console runners rather than a test framework, so there is nothing to discover. Build first, then run ./eng/run-tests.sh <config>, which starts the runners with --no-build.

Font differences can fail a render test

Some Wpt_*_MatchesReference tests fail in a bare container for that reason alone. Baseline before attributing a failure to your change.

Line endings in submodule sources

Several Broiler.HTML and Broiler.CSS files are CRLF, and some are mixed within one file. An editor that rewrites the whole file normalizes them, and a two-line change then reports two thousand. Check git show --stat after committing.
