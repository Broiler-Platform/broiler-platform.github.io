The four rules everything follows

Rule 1

An abstraction never references an implementation

Broiler.Graphics depends on the image abstraction, never a codec. Broiler.UI depends on the neutral graphics core, never Direct2D. The application composition root is the only place a concrete implementation is chosen.

Rule 2

One concern has exactly one canonical owner

One mutable DOM tree, one cascade, one layout engine. A bridge may project a canonical result into another shape; it may not keep a second copy of the truth.

Rule 3

Platform code stays at the edge

No UI runtime assembly may reference Win32, WPF, COM or an HWND. The Android input providers target plain net10.0 and take primitive event data, so they build and test with no Android SDK installed.

Rule 4

The rules are tests

Architecture tests walk the project graph and fail the build on a platform-specific reference, a native handle on a public surface, or a friend-assembly grant nobody decided on.

The full architecture

Using a piece of it

You do not have to take the whole platform. The components are independently published, and several are useful on their own — a layout engine with no renderer, a UI toolkit with no browser, image codecs with no UI at all.

the common cases
dotnet add package Broiler.Layout --prerelease                  # the layout engine alone
dotnet add package Broiler.UI.All --prerelease                  # the whole UI toolkit
dotnet add package Broiler.Media.Image.Managed --prerelease      # PNG/JPEG/GIF/WebP codecs
dotnet add package Broiler.Documents.Rtf --prerelease            # one document codec
dotnet add package Broiler.Graphics --prerelease                 # neutral rendering core
dotnet add package Broiler.Graphics.Windows --prerelease         # + the Direct2D backend

Everything is prerelease and the API is not frozen. The full package index →

The evidence, and how to read it

Broiler's documentation is unusually careful about what a passing test does and does not prove. Three things are worth knowing before you quote any number from it.

Two independent WPT suites

One scores against a Chromium screenshot; the other renders both the test and the reference WPT itself declares, with no second engine. Their pass rates are deliberately not comparable, and each is blind to what the other catches.

No release totals are recorded

The test262 dashboard's release table reads "no current release-candidate run recorded", because a total belongs there only when it links to raw artifacts from an exact commit and an exact suite revision.

Failures are published

51 open rendering gaps, 84 failing tests in one runner suite, 0% code certified by a named human. Those are on the site because leaving them off would make the rest meaningless.

Contributing

A fix usually belongs in a component repository rather than the aggregate one — the renderer, CSS engine, DOM, JS engine, graphics, input, media, document codecs, UI toolkit and all three applications each live under the Broiler-Platform organisation, and the aggregate repository composes them as submodules. Write the fix at its correct layer rather than contorting it into the top level.

  • Solutions are generated from eng/solutions.json. Change the project-reference graph, then regenerate — a hand-edited .slnx is reverted by the next run.
  • Component-owned tests live in the component's own solution, inside its submodule.
  • Some Broiler.HTML and Broiler.CSS files are CRLF, and a few are mixed within one file. If a two-line change reports two thousand, your editor rewrote the line endings.
  • Each component's roadmap is the source of truth for its own work; the root roadmap holds only what crosses component boundaries.
