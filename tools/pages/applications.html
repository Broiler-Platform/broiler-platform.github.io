Applications

Three products, one component set

Each application lives in its own repository with its own platform heads, its own generated solutions and its own CI, and consumes the shared components as git submodules pinned to main. None of them is published as a NuGet package.

Browser

Broiler.Browser

Windows, Linux and Android heads over a shared Broiler.Browser.Core chrome, plus the HtmlBridge layer that binds the DOM, the renderer and the JavaScript engine into one page lifecycle.

What the three have in common

The application repositories are shaped alike on purpose. Learning one is most of learning the others.

ConventionWhat it means
One focused solution per head Each solution contains exactly its entry point's transitive closure, so opening the Windows head does not drag in Linux backends or another platform's input providers.
Solutions are generated eng/solutions.json declares entry points and platform boundaries; a generator walks the real reference graph and writes the .slnx. A hand-edit is silently reverted by the next run, and CI runs the -Verify form as its first job.
A source-only src/Broiler.App directory Shared per-platform code — clipboards, Linux input coordination — with no project of its own. Each head links the files it needs, which keeps a platform-specific file out of a neutral assembly without inventing an assembly for it.
Six build configurations Debug/Release build framework-dependent; the -Windows and -Linux variants pin a runtime identifier. A Directory.Build.props decomposes them, because MSBuild alone would build Release-Linux unoptimized with neither symbol defined.
One shared submodule setup action The nested-submodule set each application needs is defined once, in .github/actions/setup-broiler, rather than repeated across workflow jobs.
Dispatch-only release workflows Each release.yml uploads build artifacts for manual testing and creates no GitHub release, signing nothing for distribution. Store-ready signed preview packages come from the aggregate repository's Prepare Broiler Preview Package workflow, which owns the signing material.

Android is emulator-verified, not device-verified

The shared Activity/SurfaceView host, both applications, hardware-accelerated Canvas presentation, the touch/pen/keyboard/IME bridge, system-bar insets and the scoped-storage Writer flow build and run on an API 36 x86_64 emulator. Physical-device validation remains outstanding. Only Browser declares INTERNET, and cleartext traffic is disabled for both applications.

Review status differs by application

ApplicationRecord
Broiler.Browser HUMAN_REVIEW.md is PENDING for the repository. Its CODE-ASSURANCE.md reports that src/ — the heads, the shared chrome and HtmlBridge — has not adopted the per-unit assurance system either.
Broiler.Writer Carries no HUMAN_REVIEW.md at all, so no checkout of it should be described as human-approved.
Broiler.Code The .broiler-review/ records are the only claim the repository makes about what a person has actually read — which is also the mechanism it ships to everyone else.
