Component · Execution core

Broiler.VM

A NativeAOT-compatible component that executes verified bytecode artifacts. It is a host for language profiles, not a language: it owns no opcode set, no value representation and no language semantics of its own.

All milestones unaccepted 0 packages published 0 % human reviewed Native AOT contract

Read this before anything else on the page

Code exists — a fourteen-project graph implementing core contract version 1 — but no milestone is accepted, and none can be until a human reads the work. No relevant code unit carries a decision on its // Broiler-Human: line, so the generated HUMAN_REVIEW.md states PENDING. No release capability is claimed, no package is published, and no RID or support table may be issued.

The component states the consequence plainly: what has accumulated unreviewed is not paper — it is a parser over untrusted bytes, a budget enforcer, and the corpus and fuzz target that are supposed to keep both honest, which are themselves one person's reading of what the parser ought to answer.

What the core owns — and what it refuses to own

The core owns

  • Profile selection and the static profile catalog
  • Bounded artifact loading
  • The immutable verified-artifact boundary
  • The common execution lifecycle
  • Trusted resource-limit precedence and cancellation
  • Diagnostics and profile-neutral operation-result envelopes
  • The bounded binary-reading primitives every profile needs
  • The numbered core contract version that carries them all

A profile owns

  • Its format and verifier
  • Its value and frame model
  • Control flow and semantics
  • Typed result and fault payloads
  • Imports and its oracle
  • Its conformance suite

The core imposes no opcode set, no value ABI and no language-specific result cases.

Bounded mediation of guest-initiated loads and of external suspension belongs to the core; the language meaning of either belongs to the profile. That split is the component's whole design thesis.

No plug-in discovery, by contract

A profile is added by compiling it into a product and registering its descriptor directly. Broiler.VM does not discover plug-ins by scanning assemblies, loading types by name, or using a runtime extension directory, and it offers no binary plug-in ABI.

That is part of the Native AOT contract rather than a limitation to be relaxed later: every executable profile and host capability must be rooted by a direct, typed reference, or the trimmer cannot see it. Profiles reference the core; the core never references a profile.

Sharing mechanism, never semantics

Redundancy between profiles is avoided by sharing mechanism — how bytes are read safely, how a budget is charged — and never semantics. Values, frames, opcodes and syntax trees are not shared, and a new shared component is opened only through an explicit extraction gate. This is what stops a multi-profile VM from collapsing into a lowest-common-denominator core that suits no language well.

Human review gates a release, not a development step

VM-1 was built against VM-0's frozen-but-unapproved records. The owner ruled on 2026-08-28 that implementing, landing and evidencing a milestone may proceed without a review decision, and that publishing a package, claiming a RID, issuing a support table or moving any milestone to Accepted may not. At VM-6 that stops being a formality: the milestone's own gate asks that reviews be complete, so the last milestone in the roadmap cannot be met by anyone who wrote it.

The two intended first profiles

JavaScript and WebAssembly, as Broiler.VM.Profile.JavaScript and Broiler.VM.Profile.WebAssembly. Neither is planned by the core roadmap, and no core milestone depends on either existing — which is the point of the split.

Not a replacement schedule for Broiler.JS

Broiler.JS is a legacy component with its own roadmap, ledger and consumers. Broiler.VM does not depend on it, wrap it, or replace it on any schedule stated in its roadmap, and no core gate may cite its results as evidence — not its conformance results, not its measurements, not its Native AOT samples. The JavaScript profile is expected to begin from a snapshot copy of that component, taken after its in-flight fix programme lands: a fork used as a base, with no dependency edge in either direction.

This is also distinct from Browser WebAssembly: that runs managed Broiler applications on the browser's browser-wasm platform, whereas a Broiler.VM WebAssembly profile would load and execute WebAssembly guest modules.
