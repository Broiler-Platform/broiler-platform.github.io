Broiler.JS

A modular JavaScript engine for .NET that compiles JavaScript to .NET IL at runtime, with strong interop to C#. Validated against test262 — and explicit that conformance evidence is not a security claim.

HUMAN_REVIEW pending Apache-2.0 Derived from Yantra JS Not a sandbox

Broiler.JS is not a security sandbox

JavaScript host capabilities and CLR integration must be restricted by the embedding application. Untrusted scripts must not be executed on the assumption that the engine provides isolation. This component is not human-approved for preview use while its HUMAN_REVIEW.md remains PENDING.

Where the name comes from

Broiler is a backronym: Browser Infrastructure in Intermediate Language with Enhanced Reliability. The intermediate language is the point — this engine's execution strategy is to lower JavaScript into IL the CLR then JITs, rather than to interpret it.

Origins

Broiler.JS began as a fork of Yantra JS (Apache-2.0), an open-source JavaScript engine for .NET. The original Yantra JS architecture, parser and runtime design provided the foundation; Broiler.JS has since diverged substantially to pursue near-complete ECMAScript conformance.

It is maintained independently and is not an official Yantra JS version, continuation or release. The upstream authors have not reviewed or endorsed it; the name is used only for accurate provenance.

Architecture

A layered architecture derived from earlier Yantra JS concepts, now split into explicit assemblies with narrow module boundaries.

LayerAssemblies
1 · Storage and AST foundationsBroiler.JavaScript.Storage, Broiler.JavaScript.Ast — reusable primitives with no dependency on concrete built-ins
2 · Parsing and runtime modelBroiler.JavaScript.Parser turns source text into AST structures; Broiler.JavaScript.Runtime models values and arguments
3 · Engine and compilerBroiler.JavaScript.Engine hosts execution; .Compiler performs lowering; .Expressions owns the backend-neutral expression model; .ExpressionCompiler is the dynamic-IL emitter
4 · Feature satellites.BuiltIns, .Globals, .Modules, .ModuleExtensions, .Clr, .Extensions and optional host packages — added through explicit bootstrap, manifests, module initializers and registration delegates

Modularity rules

  • Core engine projects must not reference feature satellites such as .BuiltIns.
  • Feature satellites register behaviour through documented delegates rather than editing core runtime types.
  • Compliance fixes land in the narrowest owning assembly, with tests in the matching *.Tests project.
  • Lower-level projects — Storage, Ast, Parser, Runtime — must not depend on higher-level feature assemblies.

test262 conformance

Broiler.JS is validated against test262, the official ECMAScript suite maintained by TC39. What is checked in is the evidence surface, not a headline number — and the dashboard is deliberate about the difference.

AreaCurrent evidence
Full test262 script hostManual sharded original-plus-minified runner (pinned Terser, or Closure Compiler at ADVANCED for ES2026), abnormal-shard retry, provenance-rich merged triage and an authoritative terminal verdict
Tracked failuresThe generated path list scripts/compliance/test262-failures.txt is the source of truth; the documentation does not duplicate its changing count
Negative metadataOpt-in with --include-negative; an uncaught error is reported by its JavaScript name, so a phase: parse SyntaxError is matched on the type it is
async completionA marker protocol — explicit success, explicit failure, or the runner's timeout. A test that never settles, settles twice, or reports failure is a failure
Async protocol self-checkFixtures that must fail, run before every CI shard; any mismatch fails the job
$262 host hooksglobal, createRealm, detachArrayBuffer, evalScript and gc are defined; a test is excluded only for a hook it needs and does not have
module / rawBoth executed — module under --module-host with the harness preloaded as a script, raw as the file's own unmodified bytes. Per-mode totals ride on every report

No release totals are recorded

The dashboard's release-evidence and comparative-engine tables both read "No current release-candidate run recorded." A total belongs there only when it links to raw artifacts from an exact Broiler commit and an exact upstream suite revision, and a row may never claim "100% compliant" unless every supported host mode is green and every excluded category is explicitly outside the product claim.

Representative open gaps

The known-gaps document is unusually specific — each entry names the construct, the measurement and the mechanism. Three examples:

  • Per-eval compilation cost. Every direct eval compiles a fresh DynamicMethod, and JITting it is nearly all the cost — about 21 ms in Release for a body that is one call, where the same text parses in about 15 µs. Three shapes now avoid it; everything else still pays per call.
  • A delete of an eval-introduced var, read back through the closure that deleted it, throws a ReferenceError where the name should resolve outward to the global — the delete tears the binding down and a closure holds that cell directly rather than re-resolving.
  • Symbol-keyed own properties enumerate in symbol creation order rather than property creation order.

How this component is built

Broiler.JS states its development model openly. Implementation work is done primarily by a coding AI; the project reached the point where that was viable only after a substantial manual refactor restructured the inherited Yantra JS codebase into the modular, IL-centric architecture a coding AI can navigate reliably.

The maintainer directs the work, reviews changes, runs tests, drives refactors, manages inference costs and keeps the project on track. The stated consequence is that the bottleneck is maintenance bandwidth and inference cost, not coding hours — which is why the repository asks for sponsorship rather than for pull requests first.

AI-generated or AI-modified implementation must receive source-level review from a real developer before a release is described as reviewed. test262 results are valuable conformance evidence, but they do not by themselves establish security or safety. More on how that is recorded →

Roadmaps

Broiler.JS owns more open plans than any other component. The sequencing authority is the modernization roadmap; the delivery roadmap beneath it is explicitly not a sequencing or state authority.

  • Modernization — cross-track authority for performance, assembly/AOT boundaries, package decomposition, compile-ahead, context isolation, Workers and profile-led optimization
  • Measurement — the fail-closed evidence-class, A/A, candidate/control, source-identity, resource and semantic gate every performance claim passes
  • Concurrency — compile-ahead, optimizer/cache ownership, independent contexts, Worker agents, resource caps
  • Component — non-performance engine work
  • Performance campaign crosswalk — the IL campaign, Octane/probe history and optimization catalogue

Relationship to Broiler.VM

Broiler.JS is a legacy component in the platform's own terminology — and the engine every current consumer uses. Broiler.VM does not depend on it, wrap it or replace it on any published schedule, and no VM gate may cite its results as evidence. A future JavaScript VM profile is expected to begin from a snapshot copy taken after this component's in-flight fix programme lands — a fork used as a base, with no dependency edge in either direction.
