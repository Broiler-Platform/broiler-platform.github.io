Component · Platform core

Broiler.Graphics

A platform-neutral managed rendering core — BBitmap, BCanvas, deterministic CPU rasterization, text and font handling, render lists — with one presentation backend per platform. Image decoding deliberately lives outside it.

Approved, conditions 7 packages Apache-2.0 Security-sensitive interop

Packages

There is no meta-package. An application takes the core plus exactly the backends it presents with. Every package ships XML documentation and a .snupkg symbol package, is built deterministically with SourceLink, and is published to nuget.org only.

The native API declarations the backends call — entry points, ABI structs, COM contracts, library probing — no longer live here. They moved to the shared Broiler.Native packages (Broiler.Native.Windows, .Linux and .Android), which Graphics, Input and Media now all consume from nuget.org.

The core does not decode images

This is the component's central design decision. The core references the image abstraction only — Broiler.Media.Image — never an implementation. The application composition root supplies the concrete codecs:

composition root
BImageCodecs.Use(new MediaCodecCatalog(ManagedImageCodecs.CreateCodecs()));
dependency direction
Broiler.Graphics.Windows       -> Broiler.Graphics -> Broiler.Media.Image   (abstraction only)

Broiler.Graphics.Windows       -> Broiler.Native.Windows

This is read from the project files. The README's own diagram has not yet gained the Broiler.Native.* and Broiler.Media.Video.Windows edges.

Windows Direct2D The most complete backend: render-list replay, DirectWrite text, window and input integration.

Building, testing and demos

Only Debug and Release remain; the platform-suffixed configurations are obsolete. The repository has no submodules — Media, Input and Native come from nuget.org, pinned in Directory.Packages.props. The solution build covers the platform-neutral set — core, WebAssembly, Android and their test runners. The Direct2D and Linux backends are excluded from the solution build, so a plain dotnet build still does not compile them; the test script builds the host's platform suite explicitly, and packing enumerates every packable project.

build & test
git clone https://github.com/Broiler-Platform/Broiler.Graphics.git
dotnet build Broiler.Graphics.slnx -c Release
bash ./eng/run-tests.sh Release

Tests are self-hosted console runners rather than a test framework, so there is nothing for dotnet test to discover. The script runs the three neutral suites with --no-build, so they exercise exactly the binaries the build produced, then builds and runs the suite for the host it is on — the Direct2D suite under Git Bash on Windows, the Linux suite on Linux.

The Linux demo is the composition root for graphics plus input

It opens the OpenGL X11 preview window and, with explicit raw-input acknowledgement, wires Linux evdev keyboard and mouse providers while pausing delivery when the window loses focus. It also prints OS/runtime, display-server, OpenGL driver, Vulkan device and selected evdev-device diagnostics.

linux demo
dotnet run --project src/demos/Broiler.Graphics.Linux.Demo -c Debug -- \
  --window --enable-evdev-input --interactive

Preview status and security

What the review record says

  • The component is preview software and is neither fully optimized nor final.
  • Public APIs and behaviour may change while the global refactoring continues.
  • Image decoding is injected from Broiler.Media, parses complex binary input, and must be treated as security-sensitive. Do not decode untrusted input in security-sensitive environments without sandboxing, resource limits, fuzzing and additional review.
  • The Windows backend uses native Windows APIs and Direct2D/DirectWrite/DXGI/D3D interop. Correct and security-relevant usage of every involved API is not guaranteed by a first-preview review.
  • No dedicated fuzzing campaign, SAST report, dependency scan or independent security audit is recorded. This review is not a production security audit.

CI and releases

CI builds Release on Ubuntu and on Windows for every push to main and every pull request, runs the test script and the preview-version resolver's own tests, and on the Windows leg runs eng/pack.ps1 to produce and validate all seven packages, attached to the run as nuget-packages.

Publishing goes to nuget.org only. A manual dispatch dry-runs unless told otherwise and, with no explicit suffix, picks the next unused 0.1.0-preview.N by reading what nuget.org already holds for all seven packages; eng/verify-feed.ps1 then proves a clean consumer can restore the set before anything is pushed. Pushing a v* tag publishes for real, and the tag must be on the release line and not already used. eng/Broiler.Packaging.props is now a floor rather than the version, and each repository advances its own preview sequence — consumers currently pin Graphics at 0.1.0-preview.7.
