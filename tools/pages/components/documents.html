Broiler.Documents

Reads and writes rich-text interchange formats to and from a UI-free document model. Applications compose a codec catalog explicitly, codecs probe bounded byte prefixes, and a read returns a best-effort document plus diagnostics for everything it skipped or approximated.

Packages

Eleven preview packages ship, to nuget.org only. All target net10.0, ship XML documentation and a .snupkg, and are built deterministically with SourceLink. There is no meta-package — add a package per format you actually read or write.

The PDF codec is published as a preview — its application gates are not lifted

A package is not a feature: application integration keeps the read-preview and write-preview gates

Broiler.Documents.Pdf is a base PDF codec — logical text import from ISO 32000-1 files and a deterministic PDF 1.7 writer, built only from what this repository implements itself, with no third-party runtime dependency and no bundled font or codec asset. Syntax, cross-references, object streams and the Flate / ASCIIHex / ASCII85 / RunLength filters are implemented. Every remaining PDF technology is detected, skipped with its own stable diagnostic, and reachable by composing a reviewed implementation into PdfCodecServices.

It and its optional font and image providers are now in the normal pack and publish workflows. The README is explicit that package generation does not enable application features or certify PDF conformance: application integration retains the roadmap's read-preview and write-preview gates. The document CLI composes the codec read-only — it opens, converts from and renders PDF files, and writes none until PDF output passes its write-preview gate.

Recent reader work: encrypted documents open through the standard security handler (revisions 2–4 and AES-256 revision 6) with the caller's password, and the public-key handler through a caller-composed decryptor, none of which ships; image masks are carried as alpha; ICC-based colour converts through a composed profile reader. IP and licensing requirements in the roadmap are engineering release controls, not a legal opinion; patent freedom-to-operate, reciprocal-license and jurisdiction questions need the project reviewer's approval before the affected feature ships.

Per-format conformance is documented, not implied

Each codec has a conformance document that is the authoritative statement of what it honours, approximates, ignores and skips — with the tests that exercise each category named. The RTF document, for example, tabulates the control words in each category and states two properties outright: the reader is total (never throws on malformed input) and safe by default.

The DOCX reader is a good illustration of what "best-effort plus diagnostics" means in practice. Tables used to be flattened into their cell paragraphs with a diagnostic, because the model had no table shape. They are now read as a DocumentTable over the paragraphs of their cells — column widths, spans, borders, shading, header rows, row heights and nested tables — and written back as w:tbl. What the model still cannot hold is said out loud: table styles are not applied (docx.table.style), and an "exact" row height is read as a minimum (docx.table.rowheight), because a row that clipped its own text would lose content the document has.

A CLI built to be driven by a test system

Broiler.Documents.Cli creates, edits, converts, renders and compares documents. Every command has a --json form, and the exit code is a documented contract.

The two commands the rest of it exists to support both answer the same question — where are the gaps in these codecs — and both answer it structurally first, in pixels only when that is what you actually need to know:

round-trip through every format
broilerdoc roundtrip report.docx --via docx --via odt --via rtf --via html --via markdown
compare two documents, structurally or as pixels
broilerdoc compare a.docx b.docx --render --continuous --diff diff.png --tolerance 2

Component constraints

  • Target .NET 10 only.
  • No third-party runtime dependencies — including for PDF.
  • Abstraction assemblies stay platform-neutral, safe-code compatible, trimming-friendly and AOT-friendly.
  • No hidden global codec registration. There is no process-wide registry and no module initializer.

Security

The codecs parse untrusted input

RTF control words, Open XML and OpenDocument packages, HTML, and PDF object graphs all cross a parser boundary and must be treated as security-sensitive. No fuzzing campaign, dependency scan or independent security audit is recorded for this revision. Read limits and RTF sanitization are specified in ADR 0004.

Fifteen ADRs

Seven of the fifteen are PDF decisions — scope and delivery, request/result and commit semantics, security and privacy, pagination units and fonts, standards and IP provenance, the base-implementation-plus-composed-extensions model, and (ADR 0015, amending 0009) decryption: credentials, permissions and the threat model. The other eight fix component topology, document-model ownership and promotion, the codec contract and signature probe, read limits and RTF sanitization, the RTF first-release subset, the Formatting Codes projection and grammar, standards, IP, provenance and claims for every format beyond PDF, and API deprecation and removal.
