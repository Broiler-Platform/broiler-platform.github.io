MVP-0 — the Human Review workspace

Broiler Code's first useful release was not an IDE feature. It is the tool that makes the platform's own claim about itself checkable.

The claim "AI-generated code is human reviewed" was a sentence in a README backed by twelve component HUMAN_REVIEW.md files, each attesting to a whole component at one commit and going quietly out of date as the code moved. MVP-0 replaces it with something falsifiable: every source file has a known review state relative to a concrete revision of its content.

In the editor, File ▸ Open Folder… grants a directory and fills the Solution Explorer with the sources under it, so a component can be read and marked file by file. It is the folder tree rather than the solution's own list that carries them: an SDK-style project declares no compile items, and the declared model does not evaluate the implicit globs that would invent them.

Exit gates, all met: the review model depends on nothing but the workspace (asserted by CodeEditorArchitectureTests.The_Review_Model_Depends_Only_On_The_Workspace); a dirty document cannot be marked reviewed; a review cannot be recorded without a reviewer; and the editor and CI compute the same state from the same code.

Keeping Roslyn out of Broiler.Code.Core's closure is what lets a browser or Android host compose the portable classifier alone — the decision the Phase 0 payload probes measured. Broiler.Code.Review has no UI reference for a related reason: the coverage number CI publishes and the badge the editor draws are computed by the same code, so they cannot disagree.

Two capabilities, presented separately

"Runs Broiler Code" and "builds a target" are separate capabilities, and the product makes the matrix visible rather than silently changing behaviour by platform. A host reports classification-only mode whenever it has the portable classifier but not the complete semantic stack — a visible state in the status UI, not an absence of one.

HostEditing & highlightingLive C# diagnosticsAuthoritative build
Windows / LinuxLocalLocal Roslyn service Trusted local out-of-process worker; optional remote worker
AndroidLocal portable classifier Local Roslyn only if the measured footprint and target-evaluated graph delivery pass; otherwise diagnostics update after a remote build Remote isolated worker
Browser WebAssemblyLocal portable classifier Local Roslyn only if payload/memory/trimming gates pass; otherwise diagnostics update after a remote build Remote isolated worker

Offline behaviour is stated honestly: desktop builds work offline once the SDK, workloads and restored packages are present; Android and browser clients keep editing and portable syntax colouring, but compiler diagnostics and authoritative builds are unavailable when the selected remote worker cannot be reached.

Standard project files stay canonical

The initial language scope is C# on .NET 10 using SDK-style projects. .slnx, .sln and .csproj files are canonical: Broiler Code does not invent a second project format and does not write Broiler-specific metadata into a user's project. The editor, workspace, diagnostic and build contracts stay language-neutral, but a plug-in language marketplace and a general multi-language IDE are not in scope for the first release.

Performance budgets are frozen against named traces

Every number in the budgets document comes from a committed harness and a named trace, so a regression is a figure moving on a fixed input rather than a disagreement about whether a new measurement was fair. Producing the successor snapshot and analysing it are timed separately, because they have different owners and different fixes.

This is one desktop machine, not a CI fleet. Timing figures are specific to it; the machine-independent figures — lines relexed, span counts, payload bytes, reference counts — are the ones a test may assert on any host. The CI baseline row of every table is unrecorded and is owed before Phase 1 exits, and the Android and browser rows are owed before any local-semantic claim is made for those hosts.

The SampleReports fixture is deliberately in no solution: it fails to compile by design — that is what the build-worker harness measures — and including it would break build verification.

No suppression list, deliberately

Directory.Build.props carries no NoWarn list. A clean rebuild of all five solutions emits one CS8602 in Broiler.Graphics.Linux.OpenGL and three xUnit1031 in Broiler.Code.Core.Tests, and nothing else — every Broiler.Code.* project sets TreatWarningsAsErrors and compiles clean.

Both are left visible: the first is a real upstream defect, the second is fixable here. The repository is explicit that a suppression list must not be imported from a consumer repository — those were measured against a much larger graph and would hide the next real warning.

Directory.Build.targets exists only to be found: it stops the aggregate monorepo's root targets, and the reference redirects they import, from reaching these projects when the repository is checked out as a submodule there. The file itself is empty.

Continuous integration

  • Solution manifest, build and tests on both hosts, as in the other applications.
  • Phase 0 harnesses and payload probes — built, not run. The prototype, the Roslyn measurement and the two browser payloads are benchmarks whose numbers belong to a recorded baseline on a known machine, not to a shared runner. What CI protects is that they still compile.
  • Human review — coverage over this repository, reported to the run summary. The job reports rather than gates, by design.
