Application · developer detail

Broiler.Browser

Three platform heads — Windows, Linux and Android — over the shared Broiler.Browser.Core chrome, embedding the Broiler.HtmlBridge control that binds the DOM, the renderer and the JavaScript engine into one page lifecycle. Broiler.Cli, a headless command line, loads pages through the same pipeline.

HUMAN_REVIEW pending 3 heads No submodules — 11 NuGet components Apache-2.0

Preview — evaluation, testing and contribution only

APIs, repository layout and persisted formats are unstable and may change without notice. Substantial portions were developed with AI assistance, and no component is human-approved for preview use until its HUMAN_REVIEW.md names a reviewer, a reviewed commit, evidence and a decision. Broiler.JS is not a security sandbox: CLR and host capabilities must be restricted by the embedding application before running untrusted scripts. Not for production, security-critical or safety-critical use.

Getting started

The dependency components are NuGet packages, restored from nuget.org by the first build, so a plain clone is the whole checkout.

clone, build, run
git clone https://github.com/Broiler-Platform/Broiler.Browser.git
cd Broiler.Browser

dotnet build Broiler.Windows.Browser.slnx -c Release
dotnet run --project src/Broiler.Browser.Windows/Broiler.Browser.Windows.csproj -c Release
dotnet test  Broiler.Browser.Tests.slnx -c Release

Prerequisites

  • .NET SDK 10.0 or later — the repository is developed against 10.0.400.
  • Windows head — builds on Windows; targets net10.0-windows and renders through the Direct2D backend.
  • Linux head — targets net10.0. Debug-Linux/Release-Linux pin linux-x64; plain Debug/Release build framework-dependent.
  • Android head — needs the android workload. Targets net10.0-android36.0 with a minimum SDK of 24, builds android-arm64 and android-x64, and produces an .aab in Release and an .apk otherwise. Override BroilerAndroidAbis to package a single ABI.

Configurations

Every configuration name decomposes into a base — Debug or Release — and one axis, in eng/Broiler.Configurations.props.

Debug-Linux / Release-Linuxpins linux-x64 on the Linux headproject only
Debug-Windows / Release-Windowspins win-x64 on the Windows headproject only
Debug-VM / Release-VMruns script on the Broiler.VM JavaScript profilesolution or project

The runtime-identifier pairs are absent from the solutions on purpose, so a solution-level build with one fails MSB4126. The -VM pair is declared and works both ways, but it is narrower than its name: it does not remove Broiler.JS, and the repository says no page load runs on the VM yet — VmScriptEngine runs the script-only paths on Broiler.VM and delegates everything that touches a document to Broiler.JS. See docs/vm-javascript-profile.md.

A PackageReference version is a minimum

Restore takes the lowest version nuget.org has at or above it, and several minimums name a preview nuget.org does not have, so restore resolves them upward and warns NU1603 for each one. What a project actually restored is in its obj/project.assets.json — not in the .csproj.

Network and cookies

Every head creates one BrowserProfile and hands it to its BrowserApp: a cookie store and one Broiler.Net BrowserNetworkSession over it. That session is the only network the browser uses for a page — navigations, the scripts the extractor fetches, the DOM bridge's loaders (fetch, XHR, sendBeacon, module imports, stylesheets, frames) and the renderer's images, stylesheets and fonts. A cookie a navigation receives is what every one of them carries, under Fetch's credentials, CORS and SameSite rules, and document.cookie reads the same store without ever seeing an HttpOnly cookie. No loader keeps a jar of its own.

The work is staged, and the stage reports are the record of what is and is not done:

  • Stages 1–3 complete (2026-09-24) — audit, the cookie engine, and the shared transport — with most of stage 4's script gates shipped alongside. Stage 3 report.
  • Stage 4 has open items — among them an independent VM provider test, the pinned WPT cookies/fetch/xhr suites, and header CSP.
  • No third-party cookie settings (stage 5) and no persistence (stage 6): in the report's words, every cookie ends with the process.

The plan is docs/cookie-support-implementation-plan.md; the stage 1 and stage 2 reports hold the original request inventory and the engine.

Known issues

This page used to describe three consequences of building the components from checkouts: Broiler.Layout vendored as a directory, Broiler.HTML's pre-src/ reference paths, and components compiled more than once. The repository's README says all of them ended with the checkouts — nothing here compiles a component any more. What remains worth knowing before filing a bug is the NU1603 behaviour above and the stage limits under Network and cookies.

Continuous integration

ci.yml runs on every push to main and every pull request. Every job checks out without submodules — there are none.

  • Solution manifest — scripts/update-solutions.ps1 -Verify, which fails if a checked-in .slnx no longer matches the reference graph.
  • Component graph — one assembly per name across each solution's whole closure, projects and restored packages, in Debug and again in Debug-VM, which restores a different closure. Also that every project declares every build type its solution offers, and that the configuration mapping reaches every project exactly once.
  • Build — the Windows head on windows-latest, the Linux head on ubuntu-latest.
  • Tests — the shared chrome's suite and the command line's, on both hosts, because the shared chrome does clipboard and file-dialog work that is easy to make accidentally platform-specific.
  • VM profile — the suite on Linux and the Windows head under Release-VM: the browser's host code run against the VM script engine that configuration selects.
  • Android head — a separate job, since it pays for the android workload; it runs the two graph checks for its own solution.
  • Publish — Release-Windows and Release-Linux, self-contained and single-file as the release ships them. Project-level builds by necessity: no solution declares them.

Releases

release.yml is dispatch-only. Each run picks the next preview version, builds every head with it, tags the commit browser-v<version> and drafts a GitHub pre-release. The release stays a draft until someone reviews and publishes it.

browser-v0.1.0-preview.1 is a public pre-release

The tag was cut on 2026-09-30 at 5fff149, whose CI run passed, and the drafted release was published on 2026-09-30: Broiler Browser 0.1.0-preview.1. HUMAN_REVIEW.md still reads PENDING — a summary, not a repository-level approval — so it was published ahead of the exact-commit review the root roadmap sets as the release gate.

Diagnosing a page

Broiler.Cli lives in this repository now, at src/Broiler.Browser.Cli. It came over from the aggregate repository on 2026-09-24 and on the way stopped running pages its own way: it runs them on the window's pipeline. --diagnostic-dir records a bundle for a capture — every JavaScript failure as it happens, streamed so a hang still leaves one, the page's console, every document, script, stylesheet, fetch and sub-document it loaded, and a summary.md ranking the distinct failures and the platform features the page asked for and did not get.

capture with diagnostics
dotnet run --project src/Broiler.Browser.Cli/Broiler.Browser.Cli.csproj -c Release -- \
  --capture-image https://example.com/ --output page.png \
  --diagnostic-dir ./diagnostics

--analyze is for the page that renders or runs wrong and gives no clue why. It loads, runs and renders the page, and writes one directory holding everything the run produced and a report ranking what looks wrong with its HTML, CSS, JavaScript, layout, rendering and network — including a render with no scripts run, one with every layout box outlined, and one of the page as the browser window itself paints it. It always runs the page on Broiler.JS, whatever the configuration.

analyse one page
dotnet run --project src/Broiler.Browser.Cli/Broiler.Browser.Cli.csproj -c Release -- \
  --analyze https://example.com/ --output-dir analysis --verbose

Everything else it does — --evaluate-page, the layout fuzzer, the engine smoke test — is in docs/command-line.md.

Investigations worth reading

Case studies of real pages that went wrong, written to be read by whoever hits the same symptom next. Three of them moved into the Browser repository's docs/; the mediawiki study is still in the aggregate repository.

CaseWhat it turned out to be
The browser hung on pages the CLI rendered fine The render pump asked "are any timers queued" — never false on a page holding an interval — where the drains ask "is anything due in the load window". It also re-parsed the whole document per tick, on the UI thread.
IOException about a minute after a page loads Pooled-connection aborts (Windows 995). Costs nothing — but an HttpClient-per-navigation bug used to add one per load.
html5test.com's four JavaScript exceptions Three were real and fixed. The remaining one is html5test's own WebRTC probe deliberately provoking a throw to detect an absent feature — it must not be suppressed; it disappears when WebRTC ships.
Google Search, after the consent page The consent form went out with two Content-Type values and was rejected with 400. Past that, the page's anti-abuse interpreter surfaces one wrong binding much later as a TypeError that names nothing recognisable — the reported error is rarely the bug.
mediawiki.org did not look like the reference (aggregate repository) Twenty-odd general engine defects: a calc() breakpoint that made 25 @media blocks malformed, floated flex items taken out of flow, a margin collapse spent twice, bold and italic resolving to the regular face. 38.9% → 82.7% of pixels.
