For developers

Architecture

How the platform is put together

Broiler is one dependency graph split across more than twenty repositories. The rules that keep it navigable — who owns which concern, which direction a reference may point, and what a component is forbidden to know about — are asserted by tests, not only written down.

The four rules

Almost every structural decision in the platform follows from four rules. They are worth reading before the diagrams, because the diagrams are their consequence.

Rule 1

An abstraction never references an implementation

Broiler.Graphics depends on Broiler.Media.Image — the image abstraction — and never on a codec. Broiler.UI depends on the neutral graphics core and never on Direct2D. The application composition root is the only place a concrete implementation is chosen.

Rule 2

One concern has exactly one canonical owner

There is one mutable DOM tree, one cascade, one layout engine. A bridge or a renderer may project a canonical result into another shape, but it may not maintain a second copy of the truth.

Rule 3

Platform code stays at the edge

No UI runtime assembly may reference Win32, WPF, COM, an HWND or any native backend. Android input providers target plain net10.0 and take primitive event data so they are testable with no Android SDK installed at all.

Rule 4

The rules are tests

Broiler.UI.Tests walks every project and fails the build on a platform-specific reference or a native handle on a public surface. LayoutArchitectureTests locks the exact friend-assembly set. CodeEditorArchitectureTests asserts the review model depends only on the workspace.

The layer map

Each tier consumes only the tier beneath it. The renderer sits above the engine components rather than containing them, which is what allows the layout engine to be used with no renderer and the graphics core to be used with no HTML at all.

HtmlBridge

HtmlBridge is what turns a set of engine components into a browser — or, as its own README puts it, an embeddable HTML control for .NET: a live DOM, a running JavaScript realm, and the host seam, the role WebView2 fills. It connects the JavaScript engine to the canonical DOM, CSS, HTML and layout components and owns the JavaScript-facing browser behaviour that none of them should know about. On 2026-09-16 it was extracted from Broiler.Browser, with its history, into its own repository; the browser is now one embedder of it. Its boundary is versioned: htmlbridge-public-surface/v2.

The named control surface is not written yet. Today a host composes DomBridge, ScriptEngine and a layout view itself, which is what Broiler.Browser.Core does; the repository's docs/html-control.md is the plan for closing that gap against what WebView2 and MSHTML offer.

The rule that shapes it: a binding never names an engine. It names JSEAL — the JavaScript Engine Abstraction Layer, split out into Broiler.JSeal on 2026-09-19, whose contracts assembly has no references at all — and a provider names the engine. eng/jseal-budget.json records how much engine coupling each project still has, and CI recounts it on every push; the numbers may fall and may never rise. The migration is not finished: Broiler.HtmlBridge.Dom's engine references have fallen from 891 to 12 by the count in docs/jseal.md.

A new bridge assembly is justified only by a stable deployment or dependency seam — never by a single web-platform feature. Feature bindings are co-located by web-platform surface. The aggregate repository's HtmlBridge architecture record was last reconciled on 2026-07-29 and still describes three assemblies; the HtmlBridge repository's own README and docs/ are the current description.

Repository topology

The aggregate Broiler repository is a composition, not a monolith. It gathers twenty-five git submodules, each with its own remote under the Broiler-Platform organisation: eighteen components, five applications, the planned Broiler Fond, and Broiler.Terminal, an empty placeholder. Since 2026-09-29 no component lives in the aggregate tree any more — the in-tree Broiler.Layout, the Broiler.VM documents and the HtmlBridge sources were deleted and came back as submodules. What remains is the tools and tests under src/ and tests/, the cross-component documentation, and the solution files.

The aggregate itself lags behind its submodules

The aggregate's README, docs/, eng/, scripts and every top-level .slnx are unchanged since 2026-09-10. Broiler.Cli.slnx, Broiler.Wpt.slnx, Broiler.Tooling.slnx and Broiler.Tests.slnx still list projects at paths that no longer exist — the removed src/Broiler.HtmlBridge.* projects and the old nested locations inside Broiler.JS and Broiler.HTML — and the tools under src/ still reference the removed bridge projects. Whether they build has not been tested; the paths do not resolve. The aggregate has had no CI run on main since March 2026.

From nested checkouts to packages

Until September 2026, each component repository carried checkouts of the components it depended on, so that it still built standalone. The cost was that composing them compiled some components more than once — Broiler.Media five times in a Writer desktop head, Broiler.Graphics four times. Between 2026-09-11 and 2026-09-18, every component that nested another replaced those submodules with package references to nuget.org, and the applications followed. No pinned repository contains a nested checkout any more — Graphics, UI, Writer, Code and Plate keep only a leftover .gitmodules file with nothing behind it. Every component and application now takes its dependencies as packages, and a build restores each one once.

The duplicate-compilation issue ended with the checkouts

Broiler.Browser's README records that its known issues from composing checkouts — Broiler.Layout vendored as a directory, Broiler.HTML's pre-src/ reference paths, and components compiled more than once — all "ended with the checkouts", and that nothing there compiles a component any more. The trade is the usual one for packages: a consumer sees another component's published package, not its source, so a member on another repository's main may be missing from the preview it pins. The browser's package versions are minimums, and restore resolves several of them upward with an NU1603 warning each.

Broiler.Layout, once vendored inside Broiler.Browser as ordinary tracked files, has had its own repository since 2026-09-09 and is now an aggregate submodule. The browser, the renderer and the bridge now take it as a nuget.org package, like every other component.

Solutions are generated, not hand-edited

Loading a workspace should not drag in another platform's backends, another application's heads, or a benchmark harness. So every .slnx is generated: eng/solutions.json declares each entry point and the platform boundaries it must not cross, and a generator walks the real project-reference graph and writes the solution from it. A hand-edit is silently reverted by the next run.

generate · verify
pwsh scripts/update-solutions.ps1            # write the .slnx files
pwsh scripts/update-solutions.ps1 -Verify    # fail instead of writing — the CI form

The verify form is a CI job in the Browser, Code and Plate repositories, because it is what catches a new ProjectReference that was never folded into a solution; the Writer's README still describes it, but its current workflow no longer runs it. Each solution contains exactly its entry point's transitive closure — and since the components arrive as packages, and a package is not a project a solution lists, that closure is now only the repository's own projects: 2 for the Windows browser head, 3 for the Windows Writer, 6 for the Windows Code head. Broiler Code's CI has been failing since 2026-09-17: its submodules were removed, but its Linux head still references component checkout paths that no longer exist.

Build configurations

MSBuild understands only Debug and Release, and most components — Graphics, Input, Media, CSS and others — now declare only those two, having dropped their platform-suffixed configurations; the UI and Documents solutions still declare the -Windows and -Linux pairs. The applications declare more, and decompose each name into a base configuration and one axis: the Writer in its Directory.Build.props, the browser in eng/Broiler.Configurations.props. Without that decomposition, a -c Release-Linux publish builds unoptimized and with neither RELEASE nor LINUX defined.

ConfigurationDeclared byEffect

Debug-Windows / Release-WindowsWriter and Browser heads; the UI and Documents solutionsPins win-x64 on the heads; what the publish paths use
Debug-Linux / Release-LinuxWriter and Browser heads; the UI and Documents solutionsPins linux-x64 on the heads; what the publish paths use
Debug-VM / Release-VMBrowser, HtmlBridgeRuns script on the Broiler.VM JavaScript profile through Broiler.JSeal.Vm; changes what is restored, not what a solution lists

In the browser, the runtime-identifier-pinned pairs are deliberately absent from the solutions: they are published per project, and a solution-level build of a configuration a .slnx does not declare fails with MSB4126. The -VM pair is declared, so it works both ways.

Platform hosts

Windows

The most complete path: Direct2D render-list replay, DirectWrite text, Win32 window and input integration, an HWND-backed video target, and — in the Writer and Code heads — real top-level OS windows for dialogs.

Linux

OpenGL/EGL presentation over Mesa with pbuffer and opt-in X11 window surfaces; a Vulkan 1.2 loader/device path sharing the CPU-present fallback; X11 clipboard and evdev input. A GPU-native replay slice covers clear, opaque fills and rectangular clips — text, images, transforms and translucency still fall back to CPU present.

Android

One Activity containing one Broiler-owned SurfaceView. No XML layouts, no Android widgets, no MAUI. net10.0-android36.0, minimum API 24, android-arm64 plus android-x64 for the emulator. Emulator-verified; physical-device validation is still outstanding.

WebAssembly

A platform-neutral frame planner validated against a CPU oracle, plus JSImport/JSExport Canvas interop gated with [SupportedOSPlatform("browser")]. This hosts managed Broiler applications in a browser — it is not a port of the HTML/JavaScript engine. The Writer's WebAssembly CI job has been commented out since 2026-09-14, and no release includes a web build.

Broiler.VM — a host for profiles, not a language

Broiler.VM is a NativeAOT-compatible component that executes verified bytecode artifacts. The distinction it insists on is unusual and worth stating precisely: it owns no value representation and no language semantics, and its core owns no opcode set. It owns profile selection, bounded artifact loading, the verification boundary, the execution lifecycle, resource authority, diagnostics and composition evidence. Since a correction of 2026-09-25, one thing is shared as an encoding: the universal bytecode's common family — an instruction encoding whose meanings name no language — lives in Broiler.VM.Ubc, outside the core contract, and no core assembly references it (ADR 0013).

Profiles are product project families inside the component — src/Broiler.VM.Profile.<Language>* — and the core never references one; a composition root references both, which is the only direction that exists. JavaScript, WebAssembly and MachineCode profiles exist, none of them accepted. A profile is added by compiling it into a product and registering its descriptor directly — there is no assembly scanning, no load-by-name, no extension directory and no binary plug-in ABI, because every executable profile must be rooted by a direct typed reference for Native AOT. Redundancy between profiles is avoided by sharing mechanism — how bytes are read safely, how a budget is charged — and now that one encoding; never semantics.

Implemented, evidenced, published — and entirely unaccepted

Thirteen boundary records, a graph of thirty-one projects and 113 edges, a composition register of eleven roots that advertises none, and an 87-artifact malformed-input corpus exist. The milestone ledger (updated 2026-09-28) records VM-0 through VM-7 as in progress and unaccepted — VM-7, the native artifact form, has an x86-64 backend that executes and an arm64 backend that only emits. No milestone is accepted, because no relevant code unit carries a human decision: the generated HUMAN_REVIEW.md reads PENDING, 0 of 5,773 relevant units, and says no package may be published and no RID claimed until that changes. Eight packages — the three core ones and five profile-family ones — were published to nuget.org on 2026-09-23 regardless, while it read PENDING; the ledger records the publication and moves no row for it. No runtime identifier is claimed.

Broiler.JS remains the default engine for every current consumer; Broiler.VM does not depend on it, wrap it, or replace it on any stated schedule. The VM path is an opt-in configuration: HtmlBridge's and the browser's Debug-VM / Release-VM run the script-only paths on the VM JavaScript profile through Broiler.JSeal.Vm, and hand document-bearing ones to Broiler.JS, which stays in the graph — in the browser's words, no page load runs on the VM yet.
