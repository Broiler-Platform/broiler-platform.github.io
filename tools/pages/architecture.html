Architecture

How the platform is put together

Broiler is one dependency graph split across more than a dozen repositories. The rules that keep it navigable — who owns which concern, which direction a reference may point, and what a component is forbidden to know about — are asserted by tests, not only written down.

The four rules

Almost every structural decision in the platform follows from four rules. They are worth reading before the diagrams, because the diagrams are their consequence.

Rule 1

An abstraction never references an implementation

Broiler.Graphics depends on Broiler.Media.Image — the image abstraction — and never on a codec. Broiler.UI depends on the neutral graphics core and never on Direct2D. The application composition root is the only place a concrete implementation is chosen.

Rule 2

One concern has exactly one canonical owner

There is one mutable DOM tree, one cascade, one layout engine. A bridge or a renderer may project a canonical result into another shape, but it may not maintain a second copy of the truth.

Rule 3

Platform code stays at the edge

No UI runtime assembly may reference Win32, WPF, COM, an HWND or any native backend. Android input providers target plain net10.0 and take primitive event data so they are testable with no Android SDK installed at all.

Rule 4

The rules are tests

Broiler.UI.Tests walks every project and fails the build on a platform-specific reference or a native handle on a public surface. LayoutArchitectureTests locks the exact friend-assembly set. CodeEditorArchitectureTests asserts the review model depends only on the workspace.

The layer map

Each tier consumes only the tier beneath it. The renderer sits above the engine components rather than containing them, which is what allows the layout engine to be used with no renderer and the graphics core to be used with no HTML at all.

HtmlBridge

HtmlBridge is what turns a set of engine components into a browser. It connects the JavaScript engine to the canonical DOM, CSS, HTML and layout components and owns the JavaScript-facing browser behaviour that none of them should know about. It lives in the Broiler.Browser repository, next to the application that needs it. Its boundary is versioned: htmlbridge-public-surface/v2.

A new bridge assembly is justified only by a stable deployment or dependency seam — never by a single web-platform feature. Feature bindings are co-located by web-platform surface.

Repository topology

The aggregate Broiler repository is a composition, not a monolith. Twelve components and applications are git submodules with their own remotes under the Broiler-Platform organisation; what remains in the aggregate repository is Broiler.Layout, the integration libraries, and the tools and tests under src/ and tests/.

Why components nest each other

Each component repository carries checkouts of the components it depends on, so that it still builds standalone. That is a deliberate trade, and it has a cost the repositories state openly:

Known issue: some components compile more than once

Because a component references its own nested checkouts by literal relative path, composing them in an application means Broiler.Media is compiled five times in a Writer desktop head, Broiler.Graphics four times, and several others twice. Every nested gitlink points at the same commit as the top-level one, so the duplicates are assembly-identical and no reference conflict is reported — but it is wasted work, and it violates the one-project-per-assembly-identity rule. Broiler.CSS and Broiler.HTML already avoid it with a $(BroilerDomPath) / $(BroilerGraphicsPath) property hook; the fix is to give the remaining components the same hook upstream. The solution generator already folds nested paths onto the top-level ones, so the .slnx files list each assembly once.

Broiler.Layout is the one exception to the submodule pattern: it has no standalone repository, so Broiler.Browser vendors it as ordinary tracked files. Both Broiler.HTML.Core and the bridge reach it as ..\..\..\Broiler.Layout\, which resolves to the repository root either way — so should the component ever be published, the directory can be replaced by a submodule at the same path with no reference changes.

Solutions are generated, not hand-edited

Loading a workspace should not drag in another platform's backends, another application's heads, or a benchmark harness. So every .slnx is generated: eng/solutions.json declares each entry point and the platform boundaries it must not cross, and a generator walks the real project-reference graph and writes the solution from it. A hand-edit is silently reverted by the next run.

generate · verify
pwsh scripts/update-solutions.ps1            # write the .slnx files
pwsh scripts/update-solutions.ps1 -Verify    # fail instead of writing — the CI form

The verify form is the first job in every application repository's CI, because it is what catches a new ProjectReference that was never folded into a solution. Each solution contains exactly its entry point's transitive closure — 80 projects for the Windows browser head, 54 for the Windows Writer, 38 for the Windows Code head.

Six build configurations

MSBuild understands only Debug and Release. Broiler's heads declare six, so a Directory.Build.props in each application repository decomposes them — without it, a -c Release-Linux build is unoptimized and has neither RELEASE nor LINUX defined.

ConfigurationEffect
Debug / ReleaseFramework-dependent; builds the platform-neutral set only
Debug-Windows / Release-WindowsAdds the Direct2D backend and Windows heads; pins win-x64
Debug-Linux / Release-LinuxAdds the OpenGL/Vulkan backends and Linux heads; pins linux-x64

A plain dotnet build therefore does not compile the Direct2D backend. Platform projects are excluded from every configuration except their own.

Platform hosts

Windows

The most complete path: Direct2D render-list replay, DirectWrite text, Win32 window and input integration, an HWND-backed video target, and — in the Writer and Code heads — real top-level OS windows for dialogs.

Linux

OpenGL/EGL presentation over Mesa with pbuffer and opt-in X11 window surfaces; a Vulkan 1.2 loader/device path sharing the CPU-present fallback; X11 clipboard and evdev input. A GPU-native replay slice covers clear, opaque fills and rectangular clips — text, images, transforms and translucency still fall back to CPU present.

Android

One Activity containing one Broiler-owned SurfaceView. No XML layouts, no Android widgets, no MAUI. net10.0-android36.0, minimum API 24, android-arm64 plus android-x64 for the emulator. Emulator-verified; physical-device validation is still outstanding.

WebAssembly

A platform-neutral frame planner validated against a CPU oracle, plus JSImport/JSExport Canvas interop gated with [SupportedOSPlatform("browser")]. This hosts managed Broiler applications in a browser — it is not a port of the HTML/JavaScript engine.

Broiler.VM — a host for profiles, not a language

Broiler.VM is a NativeAOT-compatible component that executes verified bytecode artifacts. The distinction it insists on is unusual and worth stating precisely: it owns no opcode set, no value representation and no language semantics. It owns profile selection, bounded artifact loading, the verification boundary, the execution lifecycle, resource authority, diagnostics and composition evidence.

Profiles are separate components that reference the core; the core references none of them. A profile is added by compiling it into a product and registering its descriptor directly — there is no assembly scanning, no load-by-name, no extension directory and no binary plug-in ABI, because every executable profile must be rooted by a direct typed reference for Native AOT. Redundancy between profiles is avoided by sharing mechanism — how bytes are read safely, how a budget is charged — and never semantics.

Implemented, evidenced — and entirely unaccepted

Twelve boundary records, a fourteen-project graph implementing core contract version 1, two fixture profiles, two Native AOT composition roots, an 87-artifact malformed corpus and 318 passing tests exist. No milestone is accepted, because no relevant code unit carries a human decision — so its generated HUMAN_REVIEW.md reads PENDING and no package, RID or support claim may be issued. Broiler.JS remains the engine every current consumer uses; Broiler.VM does not depend on it, wrap it, or replace it on any published schedule.
