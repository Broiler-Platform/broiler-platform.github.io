Components

Eleven components, released independently

Almost every reusable part of Broiler is its own repository, with its own solution, its own CI and its own NuGet packages — Broiler.Layout is the exception, and lives in the aggregate checkout. An application takes the pieces it needs; nothing is bundled by default, and no abstraction ever references an implementation.

Lockstep preview versioning

Published component packages are versioned in lockstep at 0.1.0-preview.1 — a prerelease, so every install needs --prerelease. The version lives in eng/Broiler.Packaging.props, vendored per component from one canonical file. The applications are not published as packages.

Shared component constraints

Every component repository holds itself to the same set of rules. They are not aspirations — several are asserted by architecture tests that fail the build.

Target .NET 10 only

No multi-targeting, no compatibility shims for older runtimes. Platform assemblies target net10.0-windows only where they must.

No third-party runtime dependencies

Image codecs, PDF syntax, regular expressions, Unicode data and the JavaScript engine are implemented in the repository. Test tooling may use external packages; shipping assemblies may not.

Trimming- and AOT-friendly, safe code

Abstraction assemblies are platform-neutral and safe-code compatible. The Writer's desktop heads publish with NativeAOT and report zero IL2xxx/IL3xxx warnings — which is only possible because nothing in the closure needs reflection AOT cannot see through.

Explicit composition, no hidden globals

There is no process-wide mutable codec registry and no module-initializer side effect. An application builds one immutable catalog at its composition root and passes it in.

Components carried inside other components

Three components ship inside Broiler.JS as nested submodules rather than as top-level repositories. They are separately reviewed and separately licensed where their data requires it.
