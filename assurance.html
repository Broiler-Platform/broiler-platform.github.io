Assurance & human review

“Human reviewed” is a record, not a slogan

Substantial portions of Broiler were written by AI tools under maintainer direction. That does not make the output trustworthy by default — so the platform spends real engineering effort on making the claim falsifiable, and on reporting the absence of review as precisely as its presence.

The headline position

The repository is suitable only for first-preview, controlled development, testing and evaluation. It must not be presented as production-ready, security-audited, or free of defects or vulnerabilities. Several components are approved for first-preview use, usually with conditions; several review records remain pending or explicitly state that they are not approvals.

Three mechanisms, deliberately different

Per component

HUMAN_REVIEW.md

One record per component, valid only for the exact commit a human named. It requires an identity, an exact commit, test and analysis evidence, findings, an intended-use scope, a decision and an attestation.

Weakness: it attests to a whole component at one commit, and goes out of date as the code moves.

Per file

.broiler-review/

A review record per source file, committed beside the source: status, reviewer, date, the hash of the reviewed content, provenance revision and notes. Staleness is decided by content, not by commit.

Strength: a rebase does not expire a review, and a revert restores one.

Per code unit

CODE-ASSURANCE.md

Generated per-unit metadata — review state, security risk, IP risk, resource impact — fingerprinted against the version certified. One component has adopted it so far.

Strength: it measures the absence of review precisely, rather than leaving it blank.

Component review records

Every release-facing component has a record. PENDING is not an approval. The review files deliberately require a real developer to supply the evidence and sign the decision; AI tools must not select or sign it.

The aggregate HUMAN_REVIEW.md at the repository root is explicitly a summary only — not a root-level human approval. It does not replace the individual component files, reviewer attestations, conditions or pending warnings.

Per-file review: the Human Review workspace

A component record attests to a whole component at one commit, and goes out of date as the code moves. Broiler Code's Human Review workspace records the same kind of attestation per source file, against a hash of the exact content reviewed, so the state of every file is known at every revision.

coverage over any repository
dotnet run --project Broiler.Code/src/Broiler.Code.Review.Cli -- coverage --root .

Records live in .broiler-review/ beside the source and are committed, so human review becomes part of the project's history — and a pull request can be told which reviews it invalidated.

Staleness is decided by content

Not by commit. A rebase does not expire a review and a revert restores one — which is the difference between a mechanism people will maintain and one they will route around.

Coverage counts only what still holds

It counts files approved and unchanged since. A stale approval is reported separately and never counts. The result is the counterpart to the machine-checked numbers: test262 and WPT measure what a machine can prove; review coverage measures what a human has actually read.

Notes are anchored to the code

A review note follows the code it was written against through edits — and admits when it cannot follow it any further, rather than silently pointing at the wrong lines.

The editor and CI cannot disagree

Broiler.Code.Review has no UI reference at all, so the coverage number CI publishes and the badge the editor draws are computed by the same code. A dirty document cannot be marked reviewed, and a review cannot be recorded without a reviewer.

Code assurance: measuring the absence precisely

The newest layer records assurance metadata per code unit — a review state, a security risk, an IP risk and a resource impact — fingerprinted against the version a human certified. Its aggregate table has two columns that say very different things:

ColumnWhat it means
AdoptedWhether the component carries per-unit assurance metadata at all. An empty row is not a good result.
Human reviewedThe fraction of relevant code units a named human has approved against the fingerprint of the version they approved.

A component that has not adopted the system is not at 0 %

It is unmeasured — which is a weaker position, not a stronger one. One component has adopted the system so far; the other nine, and the browser's own src/, report nothing.

The one adopted component, in full

47Files scanned, all carrying an annotation
720Relevant code units, 100 % annotated (925 more exempt by predicate)
0 %Human reviewed — every relevant unit HUMAN_PENDING
47Units at High security risk (273 Medium, 398 Low, 2 None)

The high-risk list is not abstract: it is the bounded binary reader, the bounded allocator, the verifier contracts, the profile-identity parser and the resource-limit precedence — exactly the code that stands between a malformed artifact and the host.

The report is generated, not written. It is regenerated by the test run itself, which also rewrites HUMAN_REVIEW.md, the manifest and every generated source header — so the file and the code cannot drift apart.

The release policy

Development may proceed unreviewed; nothing ships unreviewed

An official release fails on any unresolved assurance state — PENDING, STALE, an unknown reviewer, a missing review, a fingerprint mismatch, or an invalid review transition. Because every relevant unit in the adopted component is PENDING, no component is currently eligible for an official release, and the components that have not adopted the system cannot be assessed against that gate at all.

Implementing, landing and evidencing a milestone may proceed without a review decision. Publishing a package, claiming a runtime identifier, issuing a support table or moving a milestone to Accepted may not.

The aggregate table is currently hand-maintained from the components' generated reports, because a platform-wide tool every component could share does not exist yet. That is exactly the kind of hand-maintained summary the policy warns against — and it is recorded in the file rather than hidden.

AI-assisted development

AI coding tools have produced or modified substantial portions of Broiler. Maintainers direct the work, run automated checks, and decide what to merge. The project's own framing is worth quoting on its terms: that workflow can increase implementation throughput, but it does not make AI output trustworthy by default.

Human reviewers are expected to read the relevant source and validate the exact release commit — not to approve an AI-generated summary of it. Component READMEs disclose AI assistance and link to commit-scoped review records.

Broiler.JS states its development model most explicitly: implementation is done primarily by a coding AI, and the maintainer directs, reviews, tests, refactors and pays for inference. The stated consequence is that the bottleneck is maintenance bandwidth and inference cost rather than coding hours.

Shared safety risks

  • Untrusted active content. Broiler.JS can parse, compile and execute JavaScript and can interact with .NET host capabilities. It is not a security sandbox — the embedding application must restrict CLR and host capabilities before running untrusted scripts.
  • Complex parser and interop boundaries. HTML, CSS, JavaScript, font, image, document and Unicode-data inputs cross parser or native-interop boundaries that require focused security review.
  • Tests are not proof. Passing unit, test262, WPT or visual-comparison tests is useful evidence but does not establish that a component is secure or defect-free.
  • No warranty. Each applicable license supplies the covered software on an “AS IS” basis, without warranties or conditions.

The safe public position, because the preview combines all of these components: first-preview only; controlled or non-hostile inputs unless the host provides isolation; no production or security-sensitive use without further review; re-review required after source changes to reviewed commits; and public preview notes must preserve the safety warnings from the component reviews.
