Broiler.DOM

The canonical, dependency-free DOM and HTML parsing component. It is the only mutable tree in the platform, and it owns the engine-neutral DOM algorithms that everything else builds on.

HUMAN_REVIEW pending net10.0 Apache-2.0 2 assemblies

What it contains

AssemblyOwns
Broiler.DomDocument, node, element, attribute, mutation, range and traversal primitives. Depends on nothing but the BCL.
Broiler.Dom.HtmlHTML tokenization, document and fragment parsing, tree building and serialization. References Broiler.Dom and nothing else.

Both constraints are asserted by tests in the aggregate repository — Future_Dom_Kernel_Project_Must_Remain_Dependency_Free and Dom_Html_Depends_Only_On_The_Canonical_Dom_Component — so the dependency-free claim is checkable rather than aspirational.

Ownership boundary

Broiler.Dom is the only mutable tree and owns engine-neutral DOM algorithms. Broiler.Dom.Html owns parsing and serialization. Renderer geometry and JavaScript wrappers stay in HtmlBridge, because they depend on computed style, layout or the script runtime.

The bridge's JavaScript wrappers are not a second DOM tree — they project identity and behaviour over this one. That distinction is what stops the platform from drifting into two trees that have to be kept in sync.

What is still open

The extraction is complete: the old bridge-owned DomElement and HtmlTreeBuilder compatibility surfaces have been removed from the main pipeline. What remains is narrower — a set of specification-defined algorithms the bridge still implements only because this component exposes no equivalent API yet.

The size gap, and what it is not

Broiler.Dom is about 2,473 lines and Broiler.Dom.Html about 1,180; the bridge assembly that adapts them is about 36,080. That gap is not a size target. Closing the open items moves roughly 2,000 lines of neutral algorithm into this component and lets the bridge delete roughly 500 lines of compatibility shims outright — which is the actual goal.

Admission rules

An algorithm is admissible here only when every rule below holds. Anything that fails one stays in the bridge or belongs to another component.

  • Broiler.Dom acquires no project or package dependency.
  • Broiler.Dom.Html references Broiler.Dom and nothing else.
  • The API signature contains no JavaScript, style, layout, resource or host type, and takes no callback into bridge-owned mutable state — value and DomNode parameters only.
  • Failure is reported as a DomException carrying the spec error name, or as a return value. Callers marshal it into a DOMException; this component never constructs one.
  • Behaviour is pinned by owner-local tests before any consumer cuts over.

The consumer-side cutover order, deletions and guard changes are sequenced by the aggregate repository's root roadmap as waves 1–6, not by this component.
