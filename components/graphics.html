Component · Platform core

Broiler.Graphics

A platform-neutral managed rendering core — BBitmap, BCanvas, deterministic CPU rasterization, text and font handling, render lists — with one presentation backend per platform. Image decoding deliberately lives outside it.

Approved, conditions 7 packages Apache-2.0 Security-sensitive interop

Packages

There is no meta-package. An application takes the core plus exactly the backends it presents with. Every package ships XML documentation and a .snupkg symbol package, and is built deterministically with SourceLink.

Broiler.Graphics.Linux.OpenGLnet10.0OpenGL/EGL presentation over Mesa/EGL, with pbuffer and opt-in X11 window surfaces.

Broiler.Graphics.WebAssemblynet10.0Browser Canvas backend: a platform-neutral frame planner plus JSImport/JSExport interop gated with [SupportedOSPlatform("browser")].

The core does not decode images

This is the component's central design decision. The core references the image abstraction only — Broiler.Media.Image — never an implementation. The application composition root supplies the concrete codecs:

composition root
BImageCodecs.Use(new MediaCodecCatalog(ManagedImageCodecs.CreateCodecs()));
dependency direction
Broiler.Graphics.Windows       -> Broiler.Graphics -> Broiler.Media.Image   (abstraction only)
Broiler.Graphics.Windows       -> Broiler.Media.Video                       (declares the HWND video target)
Broiler.Graphics.Linux.OpenGL  -> Broiler.Graphics.Linux -> Broiler.Graphics
Broiler.Graphics.Linux.Vulkan  -> Broiler.Graphics.Linux -> Broiler.Graphics
Broiler.Graphics.Android       -> Broiler.Graphics
Broiler.Graphics.WebAssembly   -> Broiler.Graphics

Backend status

BackendStatus
Windows Direct2D The most complete backend: render-list replay, DirectWrite text, window and input integration.
Linux OpenGL Preview. A GPU-native replay slice covers clear, opaque fill/stroke rectangles and rectangular clips; text, images, rounded rectangles, transforms and translucent draws fall back to CPU-present — render lists replayed through the managed renderer, uploaded to an OpenGL texture/FBO, presented through an EGL pbuffer or opt-in X11 window surface.
Linux Vulkan Earliest preview. Creates a Vulkan 1.2 loader/device path when available and shares the CPU-present fallback. WSI/swapchain presentation and Vulkan command replay are still being built out.
AndroidEGL / OpenGL ES presentation surfaces and renderer.
WebAssemblyFrame planner validated against a CPU oracle; the browser Canvas interop runs on the browser-wasm runtime.

Building, testing and demos

The solution defines six configurations. Debug/Release build the platform-neutral set — core, WebAssembly, Android and their test runners. The -Windows and -Linux variants add the backends for that platform and select the matching runtime identifier. A plain dotnet build does not compile the Direct2D backend.

build & test
git clone --recurse-submodules https://github.com/Broiler-Platform/Broiler.Graphics.git
dotnet build Broiler.Graphics.slnx -c Release-Windows
bash ./eng/run-tests.sh Release-Windows

Tests are self-hosted console runners rather than a test framework, so there is nothing for dotnet test to discover. The script picks the runners the configuration produced — the Direct2D suite under -Windows, the Linux suite under -Linux, and the three neutral suites under every configuration — and starts them with --no-build, so they exercise exactly the binaries the build produced.

The Linux demo is the composition root for graphics plus input

It opens the OpenGL X11 preview window and, with explicit raw-input acknowledgement, wires Linux evdev keyboard and mouse providers while pausing delivery when the window loses focus. It also prints OS/runtime, display-server, OpenGL driver, Vulkan device and selected evdev-device diagnostics.

linux demo
dotnet run --project src/demos/Broiler.Graphics.Linux.Demo -c Debug-Linux -- \
  --window --enable-evdev-input --interactive

Preview status and security

What the review record says

  • The component is preview software and is neither fully optimized nor final.
  • Public APIs and behaviour may change while the global refactoring continues.
  • Image decoding is injected from Broiler.Media, parses complex binary input, and must be treated as security-sensitive. Do not decode untrusted input in security-sensitive environments without sandboxing, resource limits, fuzzing and additional review.
  • The Windows backend uses native Windows APIs and Direct2D/DirectWrite/DXGI/D3D interop. Correct and security-relevant usage of every involved API is not guaranteed by a first-preview review.
  • No dedicated fuzzing campaign, SAST report, dependency scan or independent security audit is recorded. This review is not a production security audit.

CI and releases

CI builds and tests both configurations on every push and pull request — Release-Linux on Ubuntu, Release-Windows on Windows — and attaches the packed packages to each run. Neither configuration alone produces the whole set, so the Windows leg packs both: it can build every project, because the Linux libraries are plain net10.0 with no runtime identifier.

Publishing is manual by default and dry-runs unless told otherwise. Pushing a v* tag publishes to nuget.org, and the tag must match the version in eng/Broiler.Packaging.props.
