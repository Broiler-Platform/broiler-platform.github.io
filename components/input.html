Broiler.Input

Device discovery, lifecycle, timing, bounded delivery, capture leases and diagnostics — one neutral abstraction per device kind, one provider package per platform. Graphics, DOM event construction, browser permissions, encoding and playback all stay outside.

Packages

One package per assembly, versioned in lockstep. Broiler.Input.All is a dependencies-only meta-package over the neutral contracts; platform backends are deliberately separate, so a consumer takes only the ones it runs on.

The Android providers need no Android SDK

This is the component's most useful architectural decision, and it is deliberate rather than a workaround. The Android providers target plain net10.0 and take primitive event data — the int and float values read from MotionEvent, KeyEvent and InputConnection — rather than referencing Mono.Android.

The host owns the Activity and the View, reads the real Android objects, and forwards the primitives. That keeps Android.Views and Java.Lang types out of the neutral contracts, and it makes the whole translation layer buildable and testable with the android workload not installed. A boundary test asserts the absence of those references.

Input assemblies do not reference Graphics, HTML, DOM, JavaScript, WPF, Windows Forms or application projects. Camera and microphone capture own no codecs, no playback and no preview UI.

What never crosses the boundary

Native handles, pointers, endpoint IDs and device paths do not appear in platform-neutral public payloads. Background Raw Input and evdev event streaming require explicit acknowledgement. Diagnostics must not emit typed text, movement timelines or native device paths by default — a keylogger-shaped diagnostic is not an acceptable default even in a debug build.

Camera and microphone

The camera contract is representative of how capture is modelled throughout. CameraFrameLease owns copied frame bytes and plane metadata, and disposing the lease invalidates its memory — there is no borrowed pointer to outlive its owner. CameraSessionOptions selects either bounded latest-frame preview or an explicit loss-sensitive delivery policy:

  • Latest-frame mode disposes an older queued frame before accepting a newer one.
  • Loss-sensitive mode uses the caller's queue capacity and overflow policy, and reports drops in CameraCaptureStatistics.
  • CameraLatestFramePreviewAdapter keeps only the latest frame without adding a Graphics dependency.

Frames carry plane layout, rotation, colour space, timestamp and frame number. Neither Broiler.Input.Camera nor its Windows provider depends on Graphics, UI, encoders, playback or a third-party camera wrapper.

Build and validation

ConfigurationBuilds
Debug / ReleaseNeutral contracts, the Android backends and their tests
Debug-Windows / Release-WindowsThe above plus the Windows providers and the contract tests
Debug-Linux / Release-LinuxThe above plus the Linux providers, the evdev diagnostic tool and the Linux tests
build & run the suites
dotnet build Broiler.Input.slnx -c Release-Windows --nologo
bash ./eng/run-tests.sh Release-Windows

A plain dotnet build uses Debug, which deliberately skips every Windows and Linux provider. The Android translation, provider lifecycle and boundary tests run on any host — the runner is platform-neutral, so it uses the base Release configuration even when the solution was built as Release-Windows.

The executable public API baseline lives at docs/api-baseline.txt; the contract-test project copies it into its output and compares it against the runtime assemblies, so an accidental public-surface change fails the run rather than shipping.
