Security & limits

What this preview is not safe for

Broiler is intended for evaluation, testing and contribution — not production, security-critical or safety-critical use. This page collects the security statements from across the platform in one place, unsoftened.

Broiler.JS is not a security sandbox

The JavaScript engine can parse, compile and execute JavaScript, and it can interact with .NET host capabilities. CLR and host capabilities must be restricted by the embedding application before running untrusted scripts. Do not execute untrusted JavaScript on the assumption that the engine provides isolation — it does not claim to.

The boundaries that need review

HTML, CSS, JavaScript, font, image, document and Unicode-data inputs all cross complex parser or native-interop boundaries. Each of the following is called out by its owning component as security-sensitive.

The bounded-input contracts that do exist

Several components specify their failure behaviour rather than leaving it to chance. These are design contracts, not audit results — but they are the difference between a component that has thought about hostile input and one that has not.

Media decoders are bounded by contract

Configurable MediaLimits cover encoded byte count, image and video dimensions, pixel and frame counts, audio channels, sample rate and duration, probe bytes and probe time, and queued and decoded memory — with checked arithmetic for dimensions, strides and allocation sizes.

Malformed data produces a bounded MediaException carrying a codec id and, where safe, a byte offset. Never unbounded allocation, hangs, silent partial success, or arbitrary exception leakage.

The RTF reader is total and safe by default

It never throws on malformed input, and its conformance document is the authoritative statement of what it honours, approximates, ignores and skips — each category exercised by named conformance, limit and security tests.

Capture leases own their memory

A CameraFrameLease owns copied frame bytes; disposing it invalidates its memory, so no borrowed pointer outlives its owner. Native handles, pointers, endpoint IDs and device paths never appear in platform-neutral public payloads.

Nothing registers itself globally

There is no process-wide mutable codec registry and no module-initializer side effect anywhere in the platform. An application builds one immutable catalog at its composition root — so what a process can decode is a decision someone made, not an accident of which assemblies got loaded.

Privacy defaults

  • Background Raw Input and evdev event streaming require explicit acknowledgement.
  • Diagnostics must not emit typed text, movement timelines or native device paths by default — a keylogger-shaped diagnostic is not an acceptable default even in a debug build.
  • On Android, only the Browser declares INTERNET, and cleartext traffic is disabled for both applications.
  • The Android input providers make no native or Java calls at all: the host reads the real Android objects and forwards primitives.

The privacy test-page suite measures coverage, not privacy

Broiler runs the DuckDuckGo privacy test corpus against itself and Chromium and compares probe by probe. That measures which probes Broiler can carry out at all. Nothing in it is a privacy result for Broiler — including agreement with Chromium, which means the probe ran, not that the answer was the right one. Details →

What is absent

No component records any of the following

  • A dedicated fuzzing campaign (one fuzz target exists, in Broiler.VM, unreviewed)
  • A SAST report
  • A dependency scan
  • An independent security audit

WebRTC, media devices, getUserMedia, peer connections, data channels, ICE/STUN/TURN/DTLS/SRTP/SCTP/RTP and browser WebSocket are absent, and the roadmap forbids exposing shape-compatible objects backed by no transport, capture or media behaviour. Accessibility semantics, keyboard-only operation and screen-reader behaviour have no recorded evidence — do not rely on them for an accessibility conformance claim.

Why the test results do not close this

The platform is explicit that conformance evidence is not security evidence:

Passing unit, test262, WPT or visual-comparison tests is useful evidence but does not prove that a component is secure or defect-free.

And separately, that a review is scoped to a commit: PENDING is not an approval, and an approval recorded against an older commit does not cover current source. How review status is recorded →

The safe public position

Because the preview application combines all of these components, the aggregate review record states the position that should be used when describing Broiler to anyone:

  • First-preview only.
  • Controlled or non-hostile inputs only, unless the host provides isolation.
  • No production or security-sensitive use without further review.
  • Re-review required after source changes to reviewed commits.
  • Public preview notes must preserve the safety warnings from the component reviews.

Each applicable license supplies the covered software on an “AS IS” basis, without warranties or conditions.

Reporting a problem

Security-relevant issues belong with the component that owns the code. The component repositories live under github.com/Broiler-Platform, and the aggregate repository is MaiRat/Broiler. If you are not sure which component owns a boundary, the canonical-owners table is the fastest way to find out.
